# Глава 12. Композиция, наследование и полиморфизм

## Зачем нужна эта глава

ООП в C++ часто начинают объяснять с наследования: создают `Animal`, затем `Cat` и `Dog`, рисуют дерево классов и объявляют это архитектурой. Такой порядок создаёт опасную привычку — искать базовый класс раньше, чем сформулирована задача.

В реальном C++ большая часть хорошего проектирования начинается с другого вопроса:

> Из каких значений и компонентов состоит объект и кто чем владеет?

Если передатчик использует генератор сигнала, это отношение «имеет», а не «является». Значит, естественное решение — композиция. Наследование становится полезным, когда несколько типов действительно должны взаимозаменяемо использоваться через общий контракт во время выполнения.

В этой главе ты пройдёшь путь в безопасном порядке: композиция → интерфейс → наследование → динамический полиморфизм → владение полиморфными объектами.

## Что ты будешь уметь после главы

Ты сможешь:

- отличать отношение «имеет» от отношения «является»;
- проектировать объект из небольших компонентов;
- предпочитать композицию наследованию для повторного использования реализации;
- объявлять абстрактный интерфейс с виртуальным деструктором;
- использовать `virtual`, `override`, `final` и чисто виртуальные функции;
- хранить полиморфные объекты через `std::unique_ptr<Base>`;
- распознавать object slicing;
- понимать, когда полиморфизм не нужен и достаточно значения, `enum class`, шаблона или `std::variant`;
- рисовать простой граф владения до выбора умного указателя.

## 1. Объект как значение с контрактом

Класс не обязан участвовать в наследовании. Чаще всего класс — это самостоятельный тип, который хранит данные и поддерживает их инвариант.

```cpp
class FrequencyRange {
public:
    FrequencyRange(double low, double high);

    double low() const noexcept;
    double high() const noexcept;
    double width() const noexcept;

private:
    double low_;
    double high_;
};
```

Такой тип полезен уже сам по себе. Не нужно создавать `BaseRange`, чтобы класс считался объектно-ориентированным.

## 2. Композиция: объект имеет другие объекты

Композиция означает, что один объект содержит или использует другие объекты как свои части.

```cpp
class Oscillator {
public:
    double sample(double time) const;
};

class Transmitter {
public:
    explicit Transmitter(Oscillator oscillator)
        : oscillator_(std::move(oscillator)) {}

private:
    Oscillator oscillator_;
};
```

`Transmitter` **имеет** `Oscillator`. Передатчик не является разновидностью генератора, поэтому наследование здесь искажало бы смысл.

Преимущества композиции:

- зависимости видны в полях и конструкторе;
- время жизни компонентов обычно понятно;
- компоненты можно тестировать отдельно;
- внутренняя реализация не становится частью контракта наследования;
- изменение компонента меньше затрагивает остальную систему;
- нет риска срезки и сложного виртуального поведения.

Если компонент небольшой и должен жить столько же, сколько владелец, храни его прямо по значению. Умный указатель нужен не потому, что поле является классом, а когда нужны особое время жизни, полиморфизм или отложенное создание.

## 3. Наследование: тип является частным случаем другого типа

Публичное наследование выражает отношение «является». Если `GainProcessor` публично наследуется от `Processor`, любой код, которому обещан `Processor`, должен корректно работать с `GainProcessor`.

```cpp
class Processor {
public:
    virtual ~Processor() = default;
    virtual double apply(double sample) const = 0;
};

class GainProcessor final : public Processor {
public:
    explicit GainProcessor(double gain) : gain_(gain) {}

    double apply(double sample) const override {
        return sample * gain_;
    }

private:
    double gain_;
};
```

Здесь `Processor` задаёт контракт, а `GainProcessor` предоставляет одну реализацию.

Проверка здравого смысла:

- Можно ли сказать: «`GainProcessor` является `Processor`»?
- Выполняет ли производный тип весь контракт базового?
- Не требует ли вызывающий код проверять конкретный производный тип?
- Нужен ли выбор реализации именно во время выполнения?

Если ответы сомнительны, сначала попробуй композицию.

## 4. Виртуальные функции и динамический полиморфизм

Виртуальная функция выбирает реализацию по фактическому типу объекта во время выполнения.

```cpp
const Processor& processor = gainProcessor;
const double output = processor.apply(input);
```

Хотя статический тип переменной — `const Processor&`, будет вызван `GainProcessor::apply()`.

Ключевые слова:

- `virtual` сообщает, что функция участвует в динамическом полиморфизме;
- `= 0` делает функцию чисто виртуальной, а класс — абстрактным;
- `override` просит компилятор проверить, что функция действительно переопределяет базовую;
- `final` запрещает дальнейшее переопределение функции или наследование от класса.

Всегда используй `override` в производном классе. Без него опечатка в сигнатуре может незаметно создать новую функцию вместо переопределения.

```cpp
class BadProcessor : public Processor {
public:
    // Ошибка будет обнаружена благодаря override:
    double apply(float sample) const override;
};
```

## 5. Почему базовому классу нужен виртуальный деструктор

Если объект производного типа уничтожается через указатель на базовый класс, деструктор базового класса должен быть виртуальным.

```cpp
class Processor {
public:
    virtual ~Processor() = default;
    virtual double apply(double sample) const = 0;
};
```

Теперь `std::unique_ptr<Processor>` правильно вызовет сначала деструктор производного объекта, затем базового.

Без виртуального деструктора удаление производного объекта через `Base*` приводит к неопределённому поведению. Практическое правило:

> Если класс предназначен для полиморфного использования, объяви виртуальный деструктор.

## 6. Владение через `std::unique_ptr<Base>`

Абстрактный класс нельзя хранить по значению: у него нет полной реализации. Кроме того, разные производные объекты могут иметь разные размеры. Для единоличного владения полиморфным объектом подходит `std::unique_ptr<Base>`.

```cpp
std::unique_ptr<Processor> processor =
    std::make_unique<GainProcessor>(2.0);
```

Граф владения здесь прост:

```text
unique_ptr<Processor>  ───── owns ─────>  GainProcessor
```

Владелец один. Когда `unique_ptr` уничтожается, уничтожается и объект. `shared_ptr` не нужен.

Для временного невладеющего доступа передавай `Processor&`, `const Processor&` или, если допустимо отсутствие объекта, обычный указатель с явно документированным невладеющим смыслом.

## 7. Object slicing — срезка объекта

Срезка происходит, когда объект производного типа копируется в отдельный объект базового типа по значению. Производная часть теряется.

```cpp
Derived derived;
Base base = derived; // В base осталась только Base-часть.
```

Это особенно коварно в параметрах функций и контейнерах:

```cpp
void print(Base value);       // Может срезать производный объект.
std::vector<Base> objects;    // Производные части будут потеряны.
```

Для полиморфного невладеющего доступа используй ссылку:

```cpp
void print(const Base& value);
```

Для полиморфного владения используй умные указатели:

```cpp
std::vector<std::unique_ptr<Base>> objects;
```

Абстрактный базовый класс дополнительно защищает от случайного создания базового объекта по значению, но понимать сам механизм срезки всё равно необходимо.

## 8. Когда наследование не нужно

Не создавай иерархию автоматически, если:

- набор вариантов мал и закрыт;
- поведение можно выразить обычной функцией;
- различие задаётся данными, а не поведением;
- выбор известен во время компиляции;
- тебе нужно только повторно использовать часть реализации;
- производный тип вынужден нарушать предусловия базового;
- вызывающий код постоянно делает `dynamic_cast` для выяснения настоящего типа.

Возможные альтернативы:

- поле-компонент;
- свободная функция;
- `enum class` и обычный `switch` для простого закрытого набора;
- `std::variant` для закрытого набора разных типов;
- шаблон для выбора реализации во время компиляции;
- callback или лямбда для одного небольшого изменяемого действия.

Полиморфизм полезен, когда новые реализации должны добавляться без изменения потребителя, а конкретный тип выбирается во время выполнения: из конфигурации, плагина, фабрики или пользовательского выбора.

## 9. Разобранный пример: пайплайн обработчиков

В примере пайплайн владеет последовательностью разных обработчиков. Каждый обработчик получает один отсчёт и возвращает преобразованный.

```cpp
#include <algorithm>
#include <iostream>
#include <memory>
#include <stdexcept>
#include <utility>
#include <vector>

class Processor {
public:
    virtual ~Processor() = default;
    virtual double apply(double sample) const = 0;
};

class GainProcessor final : public Processor {
public:
    explicit GainProcessor(double gain) : gain_(gain) {}

    double apply(double sample) const override {
        return sample * gain_;
    }

private:
    double gain_;
};

class ClampProcessor final : public Processor {
public:
    ClampProcessor(double low, double high) : low_(low), high_(high) {
        if (low > high) {
            throw std::invalid_argument("low must not exceed high");
        }
    }

    double apply(double sample) const override {
        return std::clamp(sample, low_, high_);
    }

private:
    double low_;
    double high_;
};

class SignalPipeline {
public:
    void add(std::unique_ptr<Processor> processor) {
        if (!processor) {
            throw std::invalid_argument("processor must not be null");
        }
        processors_.push_back(std::move(processor));
    }

    double run(double sample) const {
        for (const auto& processor : processors_) {
            sample = processor->apply(sample);
        }
        return sample;
    }

private:
    std::vector<std::unique_ptr<Processor>> processors_;
};

int main() {
    SignalPipeline pipeline;
    pipeline.add(std::make_unique<GainProcessor>(3.0));
    pipeline.add(std::make_unique<ClampProcessor>(-1.0, 1.0));

    for (const double sample : {-0.5, 0.2, 2.0}) {
        std::cout << sample << " -> " << pipeline.run(sample) << '\n';
    }
}
```

Сборка:

```bash
clang++ -std=c++20 -Wall -Wextra -Wpedantic pipeline.cpp -o pipeline
./pipeline
```

Разбор решений:

- `Processor` — небольшой абстрактный контракт без общей изменяемой реализации;
- виртуальный деструктор делает уничтожение через базовый указатель корректным;
- `override` проверяет сигнатуры;
- конкретные классы помечены `final`, потому что их дальнейшее наследование не требуется;
- `SignalPipeline` владеет обработчиками через `unique_ptr`;
- `shared_ptr` отсутствует: совместного владения нет;
- сам пайплайн построен композицией — он **имеет** набор обработчиков;
- `std::move(processor)` явно передаёт владение в вектор.

## 10. Разобранный пример: срезка и ссылка

Следующий код компилируется и наглядно показывает разницу между передачей по значению и по ссылке.

```cpp
#include <iostream>
#include <string_view>

class FilterInfo {
public:
    virtual ~FilterInfo() = default;

    virtual std::string_view name() const {
        return "generic filter";
    }
};

class GainFilterInfo final : public FilterInfo {
public:
    std::string_view name() const override {
        return "gain filter";
    }
};

void printByValue(FilterInfo info) {
    std::cout << "By value: " << info.name() << '\n';
}

void printByReference(const FilterInfo& info) {
    std::cout << "By reference: " << info.name() << '\n';
}

int main() {
    const GainFilterInfo gain;
    printByValue(gain);
    printByReference(gain);
}
```

Ожидаемый вывод:

```text
By value: generic filter
By reference: gain filter
```

В `printByValue` создаётся новый отдельный `FilterInfo`, поэтому производная часть срезана. В `printByReference` новый объект не создаётся, ссылка продолжает обозначать исходный `GainFilterInfo`, и виртуальный вызов выбирает производную реализацию.

## Связь с MATLAB

MATLAB поддерживает классы и наследование, но переход к C++ добавляет особенно важные вопросы:

- объект хранится по значению, по ссылке или через указатель;
- кто владеет объектом;
- когда объект уничтожается;
- копируется ли только базовая часть;
- имеет ли базовый класс виртуальный деструктор;
- нужен ли выбор реализации во время выполнения.

В MATLAB handle-классы ведут себя как ссылочные объекты, а value-классы — как значения. В C++ это не один переключатель класса: способ хранения и передачи явно виден в интерфейсе. Не переноси привычку «всё сложное сделать handle-объектом» в повсеместный `shared_ptr`.

Знакомый вычислительный пайплайн удобно представлять композицией этапов. Виртуальный интерфейс нужен лишь тогда, когда этапы действительно имеют разные реализации и выбираются во время выполнения.

## Типичные ошибки

1. **Наследование ради повторного использования кода.** Часто лучше вынести общий компонент и включить его в оба класса.
2. **Глубокая иерархия.** Чем больше уровней, тем труднее понимать контракт и время жизни.
3. **Базовый класс без виртуального деструктора.** Уничтожение через базовый указатель становится некорректным.
4. **Забытый `override`.** Ошибка сигнатуры может остаться незамеченной.
5. **Передача полиморфного объекта по значению.** Возникает object slicing.
6. **`std::vector<Base>` для разных производных типов.** Производные части теряются; используй `unique_ptr<Base>` при владении.
7. **`shared_ptr` по умолчанию.** Совместное владение усложняет жизненный цикл и может образовать циклы.
8. **Публичный сеттер в базовом классе, который производный тип не может честно поддержать.** Это нарушение контракта подстановки.
9. **Избыточное `protected`-состояние.** Производные классы становятся зависимы от внутреннего устройства базы.
10. **Вызов виртуальной функции из конструктора или деструктора.** Полная производная часть в этот момент ещё не создана или уже уничтожена.
11. **Постоянный `dynamic_cast`.** Часто общий интерфейс выбран неверно.
12. **Фабрика, возвращающая голый владеющий указатель.** Владение становится неясным.
13. **Пустой базовый интерфейс «на будущее».** Абстракция должна обслуживать существующий контракт.
14. **Полиморфизм для закрытого набора из двух простых значений.** `enum class` или `variant` могут быть яснее.

## Упражнения

### Уровень 1. Композиция без наследования

Создай классы `Oscillator` и `Transmitter`.

- `Oscillator` хранит частоту и вычисляет `sin(2πft)`.
- `Transmitter` содержит `Oscillator` по значению и коэффициент усиления.
- Метод `Transmitter::sample(time)` возвращает усиленный отсчёт.
- Некорректная частота должна отвергаться.

Объясни, почему `Transmitter : public Oscillator` был бы неверным отношением.

<details>
<summary>Подсказка</summary>

Передатчик использует генератор, но не является генератором. Передай `Oscillator` в конструктор `Transmitter` и сохрани его полем. Для числа π можно использовать `std::numbers::pi_v<double>` из `<numbers>`.

</details>

### Уровень 2. Новый обработчик в пайплайне

Добавь к разобранному примеру `OffsetProcessor`, который прибавляет смещение. Затем добавь `AbsoluteProcessor`, который возвращает модуль отсчёта.

Требования:

- не менять интерфейс `Processor`;
- не добавлять проверки конкретных типов в `SignalPipeline`;
- владение остаётся единоличным;
- добавить несколько проверок ожидаемого результата.

<details>
<summary>Подсказка</summary>

Каждый новый обработчик должен публично наследоваться от `Processor`, реализовать `apply(double) const` и использовать `override`. Передавай новый объект через `std::make_unique<...>()`.

</details>

### Уровень 3. Выбери архитектуру и защити решение

Нужно представить тип подкадра: `Empty`, `Data`, `Sync`. Набор типов фиксирован. В первой версии у каждого типа есть только имя и числовой код. Во второй версии каждый тип должен по-разному отображать данные в сетку, а новые реализации могут подключаться из конфигурации.

Предложи по решению для обеих версий. Рассмотри:

- `enum class`;
- `std::variant`;
- иерархию с виртуальным интерфейсом;
- владение через `unique_ptr`.

Напиши короткий прототип более сложной версии и объясни, почему ты не используешь наследование в простой.

<details>
<summary>Подсказка</summary>

Для фиксированного набора простых значений начни с `enum class` и `switch`. Если типы хранят разные данные, но набор закрыт, рассмотри `variant`. Открытый набор взаимозаменяемого поведения во время выполнения — сильный аргумент в пользу виртуального интерфейса.

</details>

## Вопросы для самопроверки

1. Чем отношение «имеет» отличается от отношения «является»?
2. Почему композицию обычно проверяют раньше наследования?
3. Для чего нужен `override`?
4. Когда базовому классу нужен виртуальный деструктор?
5. Почему `unique_ptr<Base>` может владеть `Derived`?
6. Что такое object slicing?
7. Как передать полиморфный объект без владения и без срезки?
8. Почему `shared_ptr` не должен быть выбором по умолчанию?
9. Когда `enum class` лучше иерархии?
10. О чём может говорить большое количество `dynamic_cast`?

<details>
<summary>Краткие ответы</summary>

1. В первом объект содержит или использует компонент; во втором производный тип обязан выполнять контракт базового.
2. Она проще выражает владение и повторное использование без жёсткой связи и виртуального поведения.
3. Он заставляет компилятор проверить настоящее переопределение сигнатуры.
4. Когда объекты производных типов могут уничтожаться через базовый указатель.
5. `unique_ptr` поддерживает преобразование к базовому типу, а виртуальный деструктор обеспечивает корректное уничтожение.
6. Потеря производной части при копировании объекта в базовый объект по значению.
7. Через `Base&` или `const Base&`.
8. Он моделирует совместное владение, усложняет жизненный цикл и может образовывать циклы.
9. Когда набор вариантов закрыт, а различие простое и в основном задаётся данными.
10. Общий интерфейс, вероятно, не выражает нужные операции или иерархия выбрана неудачно.

</details>

## Чек-лист готовности

- [ ] Перед наследованием я проверяю возможность композиции.
- [ ] Я могу сформулировать отношение «является» для публичного наследования.
- [ ] Абстрактный интерфейс содержит виртуальный деструктор.
- [ ] Все переопределения помечены `override`.
- [ ] Я использую `final`, когда дальнейшее наследование не предусмотрено.
- [ ] Я понимаю разницу между полиморфным владением и невладеющим доступом.
- [ ] Единоличное владение выражено через `std::unique_ptr<Base>`.
- [ ] Я не передаю полиморфные объекты по значению.
- [ ] Я могу объяснить object slicing на конкретном примере.
- [ ] Я не использую `shared_ptr` без реального совместного владения.
- [ ] Я рассматриваю `enum class`, `variant`, шаблон и callback как альтернативы.
- [ ] Иерархия выражает контракт задачи, а не желание повторно использовать несколько строк кода.
