# Глава 14. Тестирование, отладка и санитайзеры

## Зачем нужна эта глава

Фраза «у меня работает» обычно означает лишь: программа один раз дала ожидаемый результат на одном входе в одной среде. Этого недостаточно.

Надёжный результат должен быть воспроизводимым. Другой человек — или ты через месяц — должен собрать проект одной понятной последовательностью команд, запустить проверки и получить объяснимый итог.

В C++ особенно опасно полагаться только на наблюдаемый вывод. Выход за границу, use-after-free или переполнение знакового целого могут некоторое время выглядеть «нормально». Тесты проверяют контракт, отладчик помогает понять состояние программы, а санитайзеры обнаруживают целые классы дефектов времени выполнения. Эти инструменты дополняют друг друга.

## Что ты будешь уметь после главы

Ты сможешь:

- писать маленькие детерминированные тесты по схеме Arrange–Act–Assert;
- проверять основной путь, границы и ошибки контракта;
- корректно сравнивать вещественные результаты;
- отделять unit-тест от интеграционного теста;
- воспроизводить сбой минимальным входом;
- ставить breakpoint, выполнять код пошагово и читать стек вызовов;
- собирать программу с AddressSanitizer и UndefinedBehaviorSanitizer;
- понимать ограничения санитайзеров;
- подключать тестовый исполняемый файл к CTest;
- исправлять первопричину, а не только симптом.

## 1. Что именно проверяет тест

Тест проверяет публично наблюдаемое обещание программы:

- результат функции;
- изменение состояния объекта;
- тип или факт ожидаемой ошибки;
- сохранение инварианта;
- взаимодействие нескольких компонентов.

Плохой тест повторяет внутренний алгоритм строка в строку. Если в алгоритме и тесте одна ошибка, они дружно согласятся. Хороший тест выводит ожидаемый результат из спецификации, простого ручного расчёта или независимого эталона.

Например, для скользящего среднего `{1, 2, 3, 4}` с окном 2 ожидаемый результат легко получить вручную: `{1.5, 2.5, 3.5}`.

## 2. Структура Arrange–Act–Assert

Даже без тестового фреймворка полезно разделять три этапа.

```cpp
// Arrange: подготовка.
const std::vector<double> input{1.0, 2.0, 3.0};

// Act: одно проверяемое действие.
const auto output = movingAverage(input, 2);

// Assert: наблюдаемое ожидание.
expectNear(output.at(0), 1.5);
```

Такой тест легче читать и диагностировать. Если подготовка огромна, вероятно, интерфейс слишком связан или тест проверяет слишком много сразу.

## 3. Какие случаи выбирать

Для функции или класса минимум подумай о четырёх группах:

1. **Обычный случай.** Типичный корректный ввод.
2. **Граница.** Пустой контейнер, один элемент, минимальный и максимальный допустимый размер.
3. **Некорректный ввод.** Нарушение предусловия и ожидаемая реакция.
4. **Регрессия.** Маленький пример, который раньше ломался и теперь защищает исправление.

Не пытайся перебрать все числа. Выбирай случаи, представляющие разные ветви и риски контракта.

## 4. Детерминированность

Одинаковый код и вход должны давать одинаковый результат проверки.

Источники нестабильности:

- случайный генератор без фиксированного seed;
- текущая дата и время;
- сетевой ресурс;
- порядок выполнения потоков;
- общий изменяемый файл;
- зависимость от локали;
- слишком жёсткое сравнение floating-point;
- сравнение производительности как функциональный тест.

Если алгоритм использует случайность, передавай генератор или seed явно. Если тесту нужен файл, создавай небольшой временный fixture с известным содержимым. Не делай unit-тест зависимым от интернета.

## 5. Сравнение вещественных чисел

Десятичная дробь часто не представима в `double` точно. Поэтому такое сравнение хрупко:

```cpp
if (calculated == expected) { /* ... */ }
```

Обычно используют абсолютный и относительный допуск:

```cpp
#include <algorithm>
#include <cmath>

bool nearlyEqual(double actual,
                 double expected,
                 double absoluteTolerance = 1e-12,
                 double relativeTolerance = 1e-9) {
    const double difference = std::abs(actual - expected);
    const double scale = std::max(std::abs(actual), std::abs(expected));
    return difference <= std::max(absoluteTolerance,
                                  relativeTolerance * scale);
}
```

Допуск должен следовать из масштаба задачи и ожидаемой численной ошибки, а не выбираться так широко, чтобы любой результат проходил тест.

## 6. Unit-, интеграционные и сквозные тесты

### Unit-тест

Проверяет небольшую единицу поведения: функцию или компактный класс. Он быстрый, локальный и точно указывает место нарушения контракта.

### Интеграционный тест

Проверяет совместную работу нескольких компонентов: парсер + модель, кодер + декодер, библиотека + файловый формат.

### Сквозной тест

Запускает программу почти как пользователь: читает конфигурацию, выполняет пайплайн, проверяет итоговый артефакт или код возврата.

Одни сквозные тесты не заменяют unit-тесты: падение сообщает, что вся система не работает, но плохо локализует причину. Одни unit-тесты тоже недостаточны: компоненты могут быть корректны по отдельности и неверно соединены.

## 7. Разобранный пример: тестируем скользящее среднее

Это один самодостаточный файл без внешнего тестового фреймворка. Мини-харнесс нужен только для понимания механики; в большом проекте удобнее использовать GoogleTest, Catch2 или другой принятый в команде фреймворк.

```cpp
#include <algorithm>
#include <cmath>
#include <cstdlib>
#include <exception>
#include <iostream>
#include <stdexcept>
#include <string_view>
#include <vector>

std::vector<double> movingAverage(const std::vector<double>& values,
                                  std::size_t window) {
    if (window == 0) {
        throw std::invalid_argument("window must be positive");
    }
    if (window > values.size()) {
        throw std::invalid_argument("window must not exceed input size");
    }

    std::vector<double> result;
    result.reserve(values.size() - window + 1);

    double sum = 0.0;
    for (std::size_t i = 0; i < window; ++i) {
        sum += values[i];
    }
    result.push_back(sum / static_cast<double>(window));

    for (std::size_t i = window; i < values.size(); ++i) {
        sum += values[i];
        sum -= values[i - window];
        result.push_back(sum / static_cast<double>(window));
    }

    return result;
}

int failures = 0;

void expect(bool condition, std::string_view message) {
    if (!condition) {
        std::cerr << "FAILED: " << message << '\n';
        ++failures;
    }
}

bool nearlyEqual(double actual, double expected, double tolerance = 1e-12) {
    return std::abs(actual - expected) <= tolerance;
}

void expectVectorNear(const std::vector<double>& actual,
                      const std::vector<double>& expected,
                      std::string_view message) {
    if (actual.size() != expected.size()) {
        expect(false, message);
        return;
    }

    for (std::size_t i = 0; i < actual.size(); ++i) {
        if (!nearlyEqual(actual[i], expected[i])) {
            expect(false, message);
            return;
        }
    }
}

template <typename Exception, typename Function>
void expectThrows(Function action, std::string_view message) {
    try {
        action();
    } catch (const Exception&) {
        return;
    } catch (const std::exception& error) {
        std::cerr << "FAILED: " << message
                  << " (wrong exception: " << error.what() << ")\n";
        ++failures;
        return;
    }

    std::cerr << "FAILED: " << message << " (no exception)\n";
    ++failures;
}

void testTypicalInput() {
    const std::vector<double> input{1.0, 2.0, 3.0, 4.0};
    expectVectorNear(movingAverage(input, 2),
                     {1.5, 2.5, 3.5},
                     "window 2 for typical input");
}

void testWindowOfOne() {
    const std::vector<double> input{-1.0, 0.5, 7.0};
    expectVectorNear(movingAverage(input, 1),
                     input,
                     "window 1 preserves samples");
}

void testInvalidWindow() {
    const std::vector<double> input{1.0, 2.0};
    expectThrows<std::invalid_argument>(
        [&input] { (void)movingAverage(input, 0); },
        "zero window is rejected");
    expectThrows<std::invalid_argument>(
        [&input] { (void)movingAverage(input, 3); },
        "oversized window is rejected");
}

int main() {
    testTypicalInput();
    testWindowOfOne();
    testInvalidWindow();

    if (failures == 0) {
        std::cout << "All tests passed\n";
        return EXIT_SUCCESS;
    }

    std::cerr << failures << " test(s) failed\n";
    return EXIT_FAILURE;
}
```

Команда сборки:

```bash
clang++ -std=c++20 -Wall -Wextra -Wpedantic tests.cpp -o tests
./tests
```

Программа должна напечатать `All tests passed` и вернуть код 0.

Что здесь важно:

- ожидаемые векторы рассчитаны независимо и малы;
- проверяется обычный и два граничных контракта;
- тест ожидает конкретный тип исключения;
- код возврата сообщает системе сборки об успехе или провале;
- один провал не останавливает остальные простые проверки.

## 8. Подключение к CTest

Минимальная схема в `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)
project(SignalExample LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(signal_tests tests.cpp)

if(CMAKE_CXX_COMPILER_ID MATCHES "Clang|GNU")
    target_compile_options(signal_tests PRIVATE -Wall -Wextra -Wpedantic)
endif()

enable_testing()
add_test(NAME signal_tests COMMAND signal_tests)
```

Воспроизводимый запуск:

```bash
cmake -S . -B build
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

`--output-on-failure` сохраняет спокойный вывод при успехе и показывает диагностику провалившегося теста.

## 9. Отладчик: наблюдать, а не угадывать

Когда тест воспроизводимо падает, не добавляй десятки случайных `std::cout`. Сначала сократи вход, затем используй отладчик.

Базовый цикл:

1. Собери Debug-версию с символами (`-g`, обычно без агрессивной оптимизации).
2. Поставь breakpoint перед подозрительной операцией.
3. Запусти программу на минимальном падающем входе.
4. Проверь параметры и локальные переменные.
5. Выполни одну строку через step/next.
6. Посмотри стек вызовов.
7. Сравни наблюдаемое состояние с инвариантом.

Пример для LLDB:

```bash
clang++ -std=c++20 -g -O0 program.cpp -o program
lldb ./program
```

Внутри LLDB:

```text
breakpoint set --name movingAverage
run
frame variable
next
step
bt
continue
```

В IDE этим действиям соответствуют breakpoint, Step Over, Step Into, Variables и Call Stack.

Оптимизированная сборка может переставлять или удалять переменные, поэтому для первой отладки удобнее `-O0`. Но дефект, проявляющийся только в Release, нужно воспроизводить с теми же флагами, постепенно добавляя диагностическую информацию.

## 10. Санитайзеры

Санитайзер добавляет инструментирование в программу и проверяет определённые классы ошибок во время выполнения.

### AddressSanitizer, ASan

Часто обнаруживает:

- выход за границы памяти;
- use-after-free;
- double free;
- некоторые утечки памяти;
- ошибки времени жизни стековых объектов.

### UndefinedBehaviorSanitizer, UBSan

Часто обнаруживает:

- переполнение знакового целого;
- недопустимые сдвиги;
- некоторые неверные преобразования и разыменования;
- деление целого на ноль;
- нарушение выравнивания.

### ThreadSanitizer, TSan

Ищет гонки данных в многопоточном коде. Его обычно запускают отдельной конфигурацией, а не вместе с ASan.

Сборка Clang/GCC с ASan и UBSan:

```bash
clang++ -std=c++20 -g -O1 \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer \
  program.cpp -o program_sanitized
./program_sanitized
```

Санитайзер проверяет только реально выполненные пути. Если тест не вызвал ошибочную ветку, отчёта не будет. Чистый запуск санитайзера не доказывает отсутствие дефектов.

## 11. Разобранный пример: ошибка границы под ASan

Этот файл **намеренно содержит дефект**. Он компилируется, но запускать его следует в учебной директории с ASan.

```cpp
#include <cstddef>
#include <iostream>
#include <vector>

int main() {
    const std::vector<int> values{10, 20, 30};

    for (std::size_t i = 0; i <= values.size(); ++i) { // Ошибка: <=
        std::cout << values[i] << '\n';
    }
}
```

Без санитайзера программа может напечатать мусор, упасть или внешне «успешно» завершиться. Это неопределённое поведение.

С ASan:

```bash
clang++ -std=c++20 -g -O1 \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer \
  out_of_bounds.cpp -o out_of_bounds
./out_of_bounds
```

Отчёт укажет выход за границу и стек вызовов. Исправление первопричины:

```cpp
for (std::size_t i = 0; i < values.size(); ++i) {
    std::cout << values[i] << '\n';
}
```

Для кода, где неверный индекс является ожидаемой внешней ошибкой, используй явную проверку или `values.at(i)`. Просто заменить `operator[]` на `at()` недостаточно, если логика цикла всё равно неверна.

## 12. Порядок расследования дефекта

Практический алгоритм:

1. Запиши точную команду сборки и запуска.
2. Сохрани минимальный вход, на котором ошибка повторяется.
3. Определи первый неверный наблюдаемый результат, а не место последнего падения.
4. Включи предупреждения и санитайзеры.
5. Поставь breakpoint перед нарушением инварианта.
6. Сформулируй гипотезу.
7. Измени одну причину.
8. Добавь регрессионный тест, который падал до исправления.
9. Запусти весь подходящий набор тестов.
10. Удали временную шумную диагностику.

Не изменяй сразу пять участков. Иначе ты не узнаешь, какая гипотеза была верной, и можешь замаскировать дефект.

## Связь с MATLAB

MATLAB предоставляет unit testing framework, breakpoints, Profiler и сообщения об индексах. В C++ рабочая идея похожа, но появляются дополнительные уровни:

- отдельные ошибки компиляции и линковки;
- неопределённое поведение вместо гарантированного сообщения MATLAB;
- явные Debug/Release-конфигурации;
- санитайзеры памяти и UB;
- необходимость тестировать владение и время жизни;
- код возврата тестового процесса, который понимает CTest или CI.

MATLAB часто сразу сообщает о выходе за границу массива. `std::vector::operator[]` в C++ не обязан этого делать. Поэтому тест, санитайзер и корректный контракт границ особенно важны.

Если эталон существует в MATLAB, используй маленькие сохранённые входы и результаты как fixtures. Обязательно зафиксируй порядок элементов, численный допуск и соглашение об индексах, чтобы не сравнивать разные контракты.

## Типичные ошибки

1. **Тестировать только один счастливый путь.** Границы остаются незащищёнными.
2. **Сравнивать `double` через `==` без численного обоснования.** Тест становится хрупким.
3. **Делать огромный тест всей системы.** При падении трудно найти причину.
4. **Повторять реализацию в тесте.** Одна ошибка может оказаться в обоих местах.
5. **Использовать случайность без фиксированного seed.** Сбой нельзя воспроизвести.
6. **Зависеть от сети или пользовательского файла в unit-тесте.** Среда становится частью случайного результата.
7. **Проверять внутренние private-детали вместо контракта.** Рефакторинг ломает тест без изменения поведения.
8. **Игнорировать код возврата тестовой программы.** CTest может не заметить провал.
9. **Исправлять симптом в месте падения.** Память могла быть повреждена раньше.
10. **Запускать санитайзер без подходящих тестовых входов.** Невыполненная ветка не проверяется.
11. **Считать чистый ASan доказательством корректности.** Это лишь один инструмент.
12. **Смешивать санитайзер и benchmark.** Инструментирование сильно меняет производительность.
13. **Отлаживать только через печать.** Состояние и стек вызовов удобнее смотреть отладчиком.
14. **Не добавлять регрессионный тест.** Исправленная ошибка может вернуться.

## Упражнения

### Уровень 1. Тесты деления

Возьми `safeDivide` из предыдущей главы и напиши проверки:

- обычное положительное деление;
- отрицательный результат;
- нулевой знаменатель;
- очень маленький ненулевой знаменатель;
- контракт для `NaN` и бесконечности.

Не ограничивайся печатью значений: тестовая программа должна возвращать ненулевой код при провале.

<summary>Подсказка</summary>

Сделай функции `expect` и `nearlyEqual`. Для `optional` отдельно проверь наличие значения, затем само значение. Решение о `NaN` сначала запиши словами, потом кодируй тестом.

</details>

### Уровень 2. Эталон для свёртки

Напиши функцию одномерной полной свёртки двух `std::vector<double>`. Подготовь тесты:

- два коротких вектора с ручным эталоном;
- единичный импульс;
- один элемент в каждом векторе;
- пустой вход согласно выбранному контракту;
- сравнение с допуском.

Подключи тестовый исполняемый файл к CTest.

<details>
<summary>Подсказка</summary>

Для ручного эталона удобно взять `{1, 2}` и `{3, 4}`: результат `{3, 10, 8}`. Единичный импульс должен сохранять второй сигнал. Не вычисляй ожидаемый результат тем же вложенным циклом внутри теста.

</details>

### Уровень 3. Расследование дефекта

Создай небольшую программу, которая сохраняет ссылку или указатель на элемент `std::vector`, затем вызывает несколько `push_back` и использует сохранённый доступ. Добейся воспроизводимого отчёта ASan.

После этого:

1. объясни причину инвалидирования;
2. исправь архитектуру, а не только размер тестового вектора;
3. добавь регрессионный тест;
4. запусти исправленную программу с ASan и UBSan;
5. запиши команды воспроизведения.

<details>
<summary>Подсказка</summary>

Перераспределение внутреннего массива `vector` инвалидирует указатели, ссылки и итераторы на элементы. Возможные исправления: не хранить такой доступ через изменение вектора, использовать индекс, заранее определить структуру данных или обеспечить время жизни другим контейнером. Один `reserve` может уменьшить вероятность, но не всегда является достаточным архитектурным контрактом.

</details>

## Вопросы для самопроверки

1. Что должен проверять unit-тест: реализацию или наблюдаемый контракт?
2. Что означают Arrange, Act и Assert?
3. Почему тест со случайным seed трудно воспроизводить?
4. Почему `double` часто нельзя сравнивать точным равенством?
5. Чем интеграционный тест отличается от unit-теста?
6. Что первым делом сделать с невоспроизводимым сбоем?
7. Какие ошибки обычно ищет ASan?
8. Проверяет ли санитайзер путь, который ни разу не выполнился?
9. Почему чистый прогон ASan не доказывает отсутствие ошибок?
10. Зачем после исправления нужен регрессионный тест?

<details>
<summary>Краткие ответы</summary>

1. Публично наблюдаемый контракт.
2. Подготовка, одно действие и проверка ожидания.
3. Каждый запуск получает другой вход и сбой может исчезнуть.
4. Многие дроби представлены приближённо; накопленные округления различаются.
5. Он проверяет взаимодействие нескольких компонентов.
6. Зафиксировать среду, команду и минимальный вход, на котором сбой повторяется.
7. Выходы за память, use-after-free, double free и родственные дефекты.
8. Нет, проверяется только выполненный код.
9. Инструмент не покрывает все классы дефектов и все пути программы.
10. Чтобы конкретная ошибка не вернулась незаметно.

</details>

## Чек-лист готовности

- [ ] Каждый тест проверяет понятный контракт.
- [ ] В тесте видны Arrange, Act и Assert.
- [ ] Есть обычные, граничные и ошибочные случаи.
- [ ] Вещественные значения сравниваются с обоснованным допуском.
- [ ] Тесты детерминированы и не зависят от сети.
- [ ] Провал возвращает ненулевой код процесса.
- [ ] Я могу запустить тесты одной последовательностью CMake/CTest-команд.
- [ ] Я умею поставить breakpoint и посмотреть стек вызовов.
- [ ] Я умею собрать программу с ASan и UBSan.
- [ ] Я понимаю, что санитайзер проверяет только выполненные пути.
- [ ] После исправления дефекта я добавляю регрессионный тест.
- [ ] Я исправляю первопричину и повторно запускаю весь подходящий набор тестов.
