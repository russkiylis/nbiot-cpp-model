# Глава 10. Копирование, перемещение и умные указатели

## Зачем нужна эта тема

C++ часто называют языком с семантикой значений. Обычный объект можно передать, вернуть, сохранить в контейнере и скопировать так же, как число. Если объект содержит `std::vector` или `std::string`, стандартные типы сами обеспечивают корректное копирование принадлежащих данных.

Но копирование большого объекта может быть дорогим или вообще не иметь смысла. Например, открытый файл или единственный компонент конвейера нельзя просто «удвоить». Для таких ситуаций C++ поддерживает перемещение: ресурс передаётся новому владельцу вместо глубокого копирования.

Умные указатели выражают владение динамическими объектами:

- `std::unique_ptr` — один владелец;
- `std::shared_ptr` — несколько владельцев общего срока жизни;
- `std::weak_ptr` — невладеющее наблюдение за объектом под `shared_ptr`.

Главное здесь не синтаксис, а модель владения. До выбора указателя нужно ответить: кому принадлежит объект и когда он должен исчезнуть?

## Результаты обучения

После этой главы ты сможешь:

- объяснить семантику значения;
- различать копирующий конструктор, копирующее присваивание, перемещающий конструктор и перемещающее присваивание;
- понимать, какие операции компилятор создаёт автоматически;
- объяснить, что на самом деле делает `std::move`;
- безопасно работать с объектом после перемещения;
- применять Rule of Zero;
- возвращать объекты по значению без ненужного страха перед копиями;
- передавать владение через `std::unique_ptr`;
- создавать динамические объекты через `std::make_unique` и `std::make_shared`;
- использовать `std::shared_ptr` только при действительно совместном сроке жизни;
- распознавать циклы `shared_ptr` и роль `std::weak_ptr`;
- выбирать сигнатуру функции в соответствии с передачей данных или владения.

## 1. Семантика значения

Для обычных типов присваивание создаёт независимое значение:

```cpp
int first = 10;
int second = first;
second = 20;
```

Изменение `second` не меняет `first`.

Стандартные контейнеры ведут себя так же:

```cpp
std::vector<int> first{1, 2, 3};
std::vector<int> second = first;
second[0] = 100;
```

Теперь `first[0]` по-прежнему равен `1`, а `second[0]` равен `100`. Вектор `second` получил собственные элементы.

Это называют глубоким логическим копированием: каждый контейнер независимо владеет своим содержимым. Точная внутренняя реализация не важна для контракта.

Семантика значения удобна, потому что локальные изменения не создают скрытого влияния на другой объект. Цена — возможное копирование данных.

## 2. Два вида копирования

### Копирующий конструктор

Создаёт новый объект из существующего:

```cpp
Widget copy = original;
```

Концептуальная сигнатура:

```cpp
Widget(const Widget& other);
```

### Копирующее присваивание

Заменяет состояние уже существующего объекта:

```cpp
copy = another;
```

Концептуальная сигнатура:

```cpp
Widget& operator=(const Widget& other);
```

Это разные операции. В первом случае объекта `copy` ещё нет, во втором он уже существует и владеет каким-то состоянием, которое нужно корректно заменить.

Если все поля класса являются нормальными значениями вроде `std::vector`, `std::string`, чисел и других безопасных классов, автоматически созданные операции обычно делают именно то, что нужно.

## 3. Перемещение

Перемещение позволяет новому объекту забрать внутренние ресурсы временного или больше не нужного объекта.

Для `std::vector` это обычно означает передачу внутреннего буфера вместо копирования каждого элемента.

Два вида операций:

```cpp
Widget(Widget&& other);             // перемещающий конструктор
Widget& operator=(Widget&& other);  // перемещающее присваивание
```

`Widget&&` здесь является rvalue-ссылкой. На первом этапе достаточно понимать её как способ принять объект, ресурсы которого разрешено забрать.

Перемещение особенно полезно для:

- больших контейнеров;
- возвращаемых значений;
- объектов с единственным владельцем;
- `std::unique_ptr`;
- элементов контейнеров при перераспределении памяти.

## 4. Что делает `std::move`

Название может ввести в заблуждение. `std::move` сам не переносит ни байта. Он преобразует выражение в форму, которая говорит:

> Этот объект больше не нужен в прежнем состоянии; разрешено вызвать перемещающую операцию.

```cpp
std::vector<int> source{1, 2, 3};
std::vector<int> destination = std::move(source);
```

Перемещение выполняет конструктор `destination`, а `std::move` только делает такой выбор возможным.

Для `std::move` нужен заголовок `<utility>`.

### Состояние после перемещения

Перемещённый стандартный объект остаётся **валидным, но его конкретное значение обычно не определено контрактом**.

С ним можно:

- уничтожить его;
- присвоить ему новое значение;
- вызвать операции, не требующие конкретного содержимого, если контракт типа это разрешает.

Не нужно предполагать, что перемещённый вектор обязательно пуст, даже если конкретная реализация часто оставляет его пустым.

Хороший стиль:

```text
переместил объект;
не читаю его прежнее содержимое;
при необходимости сначала присваиваю новое корректное значение.
```

## 5. Автоматические специальные операции

К специальным операциям класса относятся:

- конструктор по умолчанию;
- деструктор;
- копирующий конструктор;
- копирующее присваивание;
- перемещающий конструктор;
- перемещающее присваивание.

Компилятор способен создать многие из них автоматически, применяя соответствующую операцию к каждому полю.

### Rule of Zero

Если класс состоит из RAII-полей, не объявляй специальные операции без причины:

```cpp
class Dataset {
public:
    // обычные предметные конструкторы и методы

private:
    std::string name_;
    std::vector<double> values_;
};
```

`std::string` и `std::vector` уже умеют копироваться, перемещаться и уничтожаться. Компилятор соберёт корректное поведение `Dataset` из поведения полей.

### Rule of Five

Если низкоуровневый класс вручную управляет ресурсом и вынужден определять одну из операций освобождения или копирования, часто нужно осознанно рассмотреть все пять операций: деструктор, две копирующие и две перемещающие.

Для прикладного кода это чаще сигнал: ресурс следует завернуть в готовый RAII-тип и вернуться к Rule of Zero.

### `= default` и `= delete`

Можно явно попросить стандартное поведение:

```cpp
Widget(const Widget&) = default;
```

Или запретить операцию:

```cpp
Widget(const Widget&) = delete;
Widget& operator=(const Widget&) = delete;
```

Но класс с полем `std::unique_ptr` уже автоматически не копируется, потому что не копируется само поле. Не дублируй объявления без необходимости, если свойство и так ясно из состава класса.

## 6. `noexcept` и перемещение

Контейнеры стараются сохранять сильные гарантии при перераспределении. Если пользовательский перемещающий конструктор может выбросить исключение, `std::vector` иногда предпочитает копирование, когда оно доступно.

Поэтому вручную написанную перемещающую операцию, которая действительно не может выбросить исключение, обычно отмечают `noexcept`.

Не добавляй `noexcept` механически. Нарушенное обещание `noexcept` приводит к аварийному завершению программы. При Rule of Zero компилятор часто сам выводит корректное свойство из полей.

## 7. Полностью компилируемый пример: наблюдаем копирование и перемещение

Класс ниже специально печатает специальные операции. В рабочей предметной модели такие операции обычно не пишут вручную: пример нужен только для наблюдения механики.

```cpp
#include <iostream>
#include <string>
#include <utility>

class TraceValue {
public:
    explicit TraceValue(std::string name)
        : name_(std::move(name)) {
        std::cout << "Создан: " << name_ << '\n';
    }

    TraceValue(const TraceValue& other)
        : name_(other.name_ + " [копия]") {
        std::cout << "Скопирован из: " << other.name_ << '\n';
    }

    TraceValue(TraceValue&& other) noexcept
        : name_(std::move(other.name_)) {
        std::cout << "Перемещён\n";
    }

    TraceValue& operator=(const TraceValue& other) {
        if (this != &other) {
            name_ = other.name_ + " [присвоенная копия]";
        }
        std::cout << "Копирующее присваивание\n";
        return *this;
    }

    TraceValue& operator=(TraceValue&& other) noexcept {
        if (this != &other) {
            name_ = std::move(other.name_);
        }
        std::cout << "Перемещающее присваивание\n";
        return *this;
    }

    ~TraceValue() {
        std::cout << "Уничтожен: " << name_ << '\n';
    }

    [[nodiscard]] const std::string& name() const {
        return name_;
    }

private:
    std::string name_;
};

int main() {
    TraceValue original{"original"};
    TraceValue copied = original;
    TraceValue moved = std::move(original);

    std::cout << "Копия: " << copied.name() << '\n';
    std::cout << "Новый владелец: " << moved.name() << '\n';

    original = TraceValue{"новое значение"};
    std::cout << "Переиспользованный original: "
              << original.name() << '\n';
}
```

Наблюдения:

1. `copied = original` в объявлении вызывает копирующий конструктор, а не присваивание.
2. `std::move(original)` разрешает выбрать перемещающий конструктор.
3. После перемещения программа не полагается на старое имя `original`.
4. Новое присваивание делает `original` снова объектом с известным содержимым.
5. В операторах присваивания показана проверка самоприсваивания.
6. Деструкторы выполняются в обратном порядке создания объектов.

Этот пример не нужно копировать как заготовку для каждого класса. Нормальный класс со `std::string` и `std::vector` должен следовать Rule of Zero.

## 8. Возврат по значению

Не бойся возвращать `std::vector`, `std::string` или предметный объект по значению:

```cpp
std::vector<double> makeSignal(std::size_t count) {
    std::vector<double> result(count, 0.0);
    // заполнение
    return result;
}
```

Современный C++ применяет устранение копирования и перемещение. Во многих случаях результат сразу создаётся в памяти вызывающей стороны.

Не пиши `return std::move(result);` для обычной локальной переменной без специальной причины. Это может помешать оптимизации возврата. Пиши простой `return result;`.

## 9. Приём параметра и передача владения

Сигнатура функции должна показывать намерение.

### Только чтение

```cpp
void print(const Dataset& dataset);
```

Владение не передаётся, копии нет.

### Изменение существующего объекта

```cpp
void normalize(Dataset& dataset);
```

Функция не владеет объектом, но изменяет его.

### Получение собственного значения

Конструктор или функция может принять значение и переместить его в поле:

```cpp
class Report {
public:
    explicit Report(std::string title)
        : title_(std::move(title)) {}

private:
    std::string title_;
};
```

Такой стиль особенно удобен, когда функция в любом случае должна сохранить собственную строку. Вызов с временной строкой переместит её, с существующей lvalue-строкой сначала создаст копию параметра.

### Передача единственного владения

```cpp
void install(std::unique_ptr<Component> component);
```

Вызов показывает передачу владения через `std::move`.

## 10. `std::unique_ptr`

`std::unique_ptr<T>` владеет одним динамическим объектом типа `T`. Когда умный указатель уничтожается, объект автоматически освобождается.

Создавай его через `std::make_unique`:

```cpp
auto sensor = std::make_unique<Sensor>(arguments);
```

Преимущества:

- владение видно в типе;
- нет ручного `delete`;
- исключения не приводят к утечке;
- указатель нельзя случайно скопировать;
- владение можно явно передать перемещением.

### Передача владения

```cpp
std::unique_ptr<Sensor> first = std::make_unique<Sensor>();
std::unique_ptr<Sensor> second = std::move(first);
```

После перемещения `second` владеет объектом, а `first` больше не владеет им и обычно равен `nullptr`. В отличие от общего правила о перемещённых объектах, состояние перемещённого `unique_ptr` определено: он пуст.

### Доступ

```cpp
sensor->read();
Sensor& object = *sensor;
```

Перед разыменованием потенциально пустого `unique_ptr` его нужно проверить.

### Невладеющий доступ

Метод `.get()` возвращает сырой указатель-наблюдатель. Его нельзя удалять вручную и нельзя хранить дольше `unique_ptr`.

Метод `.release()` снимает владение без удаления. Он легко создаёт утечку и в обычном коде почти не нужен. Не используй его для «получения указателя».

## 11. Полностью компилируемый пример: конвейер с `unique_ptr`

Разные преобразования имеют общий интерфейс. Конвейер является единственным владельцем объектов преобразований.

```cpp
#include <algorithm>
#include <iostream>
#include <memory>
#include <stdexcept>
#include <utility>
#include <vector>

class Transform {
public:
    virtual ~Transform() = default;
    [[nodiscard]] virtual double apply(double value) const = 0;
};

class Gain final : public Transform {
public:
    explicit Gain(double factor)
        : factor_(factor) {}

    [[nodiscard]] double apply(double value) const override {
        return value * factor_;
    }

private:
    double factor_;
};

class Clamp final : public Transform {
public:
    Clamp(double minimum, double maximum)
        : minimum_(minimum), maximum_(maximum) {
        if (minimum_ > maximum_) {
            throw std::invalid_argument("Неверные границы Clamp");
        }
    }

    [[nodiscard]] double apply(double value) const override {
        return std::clamp(value, minimum_, maximum_);
    }

private:
    double minimum_;
    double maximum_;
};

class Pipeline {
public:
    void add(std::unique_ptr<Transform> transform) {
        if (!transform) {
            throw std::invalid_argument("Пустое преобразование");
        }
        transforms_.push_back(std::move(transform));
    }

    [[nodiscard]] double apply(double value) const {
        for (const auto& transform : transforms_) {
            value = transform->apply(value);
        }
        return value;
    }

private:
    std::vector<std::unique_ptr<Transform>> transforms_;
};

int main() {
    Pipeline pipeline;
    pipeline.add(std::make_unique<Gain>(2.0));
    pipeline.add(std::make_unique<Clamp>(-1.0, 3.0));

    for (double value : std::vector<double>{-2.0, 0.5, 4.0}) {
        std::cout << value << " -> " << pipeline.apply(value) << '\n';
    }
}
```

Разбор владения:

1. `make_unique<Gain>` создаёт объект и сразу помещает его под управление `unique_ptr`.
2. Параметр `Pipeline::add` принимает владение.
3. `push_back(std::move(transform))` передаёт владение элементу вектора.
4. Локальный параметр после этого пуст; удалять объект вручную не нужно.
5. При уничтожении `Pipeline` уничтожается вектор, затем каждый `unique_ptr`, затем каждое преобразование.
6. Виртуальный деструктор базового класса обязателен, потому что производные объекты уничтожаются через указатель на `Transform`.
7. `Pipeline` автоматически становится перемещаемым и некопируемым из-за поля с `unique_ptr`. Это может быть правильной моделью: один конвейер — один набор операций.

## 12. Когда динамический объект вообще нужен

Не создавай `unique_ptr` для каждого объекта. Сначала предпочитай обычное значение:

```cpp
Sensor sensor{configuration};
```

Динамическое владение оправдано, когда:

- конкретный тип выбирается во время выполнения и используется через полиморфный интерфейс;
- объект должен пережить область, где был выбран, и передаётся владельцу;
- объект слишком велик или его положение в памяти должно оставаться стабильным;
- структура данных естественно содержит динамические узлы;
- внешний API требует динамического ресурса.

Причина «объект — это класс» недостаточна. Обычные объекты классов прекрасно живут как локальные значения и поля.

## 13. `std::shared_ptr`

`std::shared_ptr<T>` хранит совместное владение. Объект уничтожается, когда исчезает последний `shared_ptr`, владеющий им.

Создание:

```cpp
auto configuration = std::make_shared<Configuration>(arguments);
```

Копирование `shared_ptr` не копирует объект `Configuration`; оно увеличивает счётчик владельцев.

`shared_ptr` уместен только если несколько независимых частей программы действительно должны совместно определять срок жизни объекта и невозможно естественно назначить одного владельца.

Не выбирай его только потому, что не решил вопрос владения. Неясная архитектура, скрытая за счётчиком ссылок, остаётся неясной.

### Цена и ограничения

- есть управляющий блок и счётчик ссылок;
- копирование указателя изменяет счётчик;
- момент уничтожения становится менее очевидным;
- потокобезопасный счётчик не делает сам объект потокобезопасным;
- циклические ссылки могут помешать освобождению.

## 14. Цикл `shared_ptr` и `weak_ptr`

Если объект `A` владеет `B` через `shared_ptr`, а `B` владеет `A` через `shared_ptr`, их счётчики никогда не достигнут нуля:

```text
A --shared--> B
^              |
|              |
---shared-------
```

Одна из связей, которая логически является наблюдением, должна быть `std::weak_ptr`.

`weak_ptr`:

- не увеличивает число владельцев;
- может сообщить, существует ли объект;
- перед использованием преобразуется во временный `shared_ptr` через `lock()`.

```cpp
if (std::shared_ptr<Node> node = weakNode.lock()) {
    node->process();
}
```

Если объект уже уничтожен, `lock()` вернёт пустой `shared_ptr`.

## 15. Связь с MATLAB

Обычные числовые массивы MATLAB воспринимаются как значения, хотя среда может откладывать фактическое копирование до изменения. Handle-классы, напротив, позволяют нескольким переменным ссылаться на один объект.

В C++ выбор виден в типах:

| Намерение | Типичный C++-тип |
|---|---|
| Независимое значение | обычный объект |
| Обязательное временное наблюдение | `T&`, `const T&` |
| Необязательное наблюдение | `T*`, `const T*` |
| Один динамический владелец | `std::unique_ptr<T>` |
| Реально совместный срок жизни | `std::shared_ptr<T>` |
| Наблюдение за shared-объектом | `std::weak_ptr<T>` |

В MATLAB копирование и совместность иногда скрыты за поведением среды или видом класса. В C++ полезно делать намерение о владении частью интерфейса.

Перемещение — новая для MATLAB-пользователя идея: объект не копируется, а отдаёт ресурсы новому владельцу. После этого старое имя ещё существует, но прежнее содержимое использовать нельзя без проверки контракта.

## 16. Типичные ошибки

### `std::move` «для ускорения» повсюду

Перемещение меняет смысл владения. Используй его, когда действительно отдаёшь объект и больше не нуждаешься в прежнем состоянии.

### Чтение прежнего содержимого после перемещения

Объект валиден, но его значение обычно не определено. Присвой новое значение перед содержательным использованием.

### `return std::move(local)`

Для обычной локальной переменной это может помешать устранению копирования. Пиши `return local;`.

### Попытка скопировать `unique_ptr`

Единственное владение нельзя размножить. Передай его через `std::move` либо пересмотри модель.

### Два владельца одного сырого адреса

Создание двух независимых умных указателей из одного `T*` приводит к двойному удалению. Создавай владельца один раз через `make_unique` или `make_shared`.

### Ручной `delete` результата `.get()`

Объект всё ещё принадлежит умному указателю и будет удалён повторно. `.get()` возвращает только наблюдателя.

### Использование `.release()` без нового владельца

Умный указатель перестаёт отвечать за объект, и возникает утечка.

### `shared_ptr` по умолчанию

Он скрывает отсутствие решения о владельце, добавляет стоимость и делает момент уничтожения менее ясным.

### Циклическое совместное владение

Счётчики не достигают нуля. Невладеющую обратную связь выражай через `weak_ptr`.

### Отсутствие виртуального деструктора

Если производный объект уничтожается через `unique_ptr<Base>`, у полиморфного базового класса должен быть виртуальный деструктор.

### `std::move` от `const`-объекта

Обычная перемещающая операция принимает изменяемый `T&&`, потому что забирает ресурсы. Из `const T` часто получится копирование, несмотря на запись `std::move`.

### Ручные специальные операции в классе со стандартными полями

Лишний деструктор или копирующий код создаёт новые места для ошибок и может повлиять на автоматическое перемещение. Начинай с Rule of Zero.

## 17. Упражнения

### Уровень 1. Семантика значения

1. Скопируй `std::vector<std::string>`, измени копию и докажи выводом, что оригинал независим.
2. Добавь объект `TraceValue` из примера в `std::vector`, сначала без `reserve`, затем с `reserve`. Сравни сообщения.
3. Перемести строку в другую переменную. Не проверяй её прежнее содержимое; присвой исходной строке новое значение и используй снова.
4. Напиши функцию, создающую большой вектор и возвращающую его по значению без `std::move` в `return`.
5. Создай `unique_ptr<int>`, передай владение второму указателю и проверь состояние первого.

<details><summary>Подсказка</summary>

Копия вектора владеет собственными элементами. Для передачи `unique_ptr` требуется `std::move`. После перемещения первого умного указателя его можно сравнить с `nullptr`.

</details>

### Уровень 2. Выбор интерфейса

Для каждой функции выбери и обоснуй тип параметра: значение, `const&`, `&`, `unique_ptr` или сырой указатель-наблюдатель.

1. Печать отчёта без сохранения объекта.
2. Нормализация существующего набора данных.
3. Сохранение собственного имени внутри нового объекта.
4. Установка единственного полиморфного обработчика.
5. Необязательное наблюдение за текущим обработчиком.

Затем реализуй класс `Report`, состоящий из `std::string` и `std::vector<double>`, не объявляя вручную специальные операции. Проверь копирование и перемещение.

<details><summary>Подсказка</summary>

Чтение без владения обычно выражается через `const&`, изменение — через `&`. Принимающий владелец полиморфного объекта может получить `unique_ptr` по значению. Наблюдение не должно создавать второго владельца.

</details>

### Уровень 3. Модель владения

1. Расширь `Pipeline`: добавь метод удаления операции и тест, доказывающий, что удалённый объект уничтожается автоматически.
2. Реши, должен ли `Pipeline` копироваться. Выбери один вариант:
   - явно оставить его только перемещаемым;
   - добавить полиморфный `clone` и реализовать глубокое копирование операций.
   Обоснуй цену выбранного решения.
3. Спроектируй граф задач, где проект владеет задачами, а задача невладеюще знает родительский проект. Определи, нужны ли вообще `shared_ptr` и `weak_ptr`, или достаточно обычного владельца и сырого указателя-наблюдателя.
4. Создай маленький пример цикла из двух `shared_ptr`, проследи отсутствие деструкторов, затем замени одну связь на `weak_ptr` и проверь исправление.
5. Нарисуй для своей программы таблицу: объект, владелец, наблюдатели, способ передачи, момент уничтожения.

<details><summary>Подсказка</summary>

Контейнер `unique_ptr` сам удаляет элемент при `erase`. Для глубокого копирования полиморфного объекта каждому конкретному типу нужна виртуальная операция, создающая новый объект того же фактического типа. В графе сначала ищи одного естественного владельца; `shared_ptr` нужен не для любой связи, а для совместного определения срока жизни.

</details>

## 18. Вопросы для самопроверки

### Что происходит при копировании `std::vector`?

Новый вектор получает независимое содержимое и владеет собственными элементами.

### Чем копирующий конструктор отличается от копирующего присваивания?

Конструктор создаёт новый объект, присваивание заменяет состояние уже существующего.

### Выполняет ли `std::move` перемещение?

Нет. Он разрешает выбрать перемещающую операцию, преобразуя категорию выражения.

### Что гарантировано после перемещения обычного стандартного объекта?

Он валиден и может быть уничтожен или получить новое значение, но конкретное прежнее содержимое обычно не гарантировано.

### Почему полезен Rule of Zero?

Стандартные RAII-поля сами правильно копируются, перемещаются и уничтожаются, поэтому ручной код управления ресурсом не нужен.

### Стоит ли бояться возврата большого объекта по значению?

Обычно нет. Компилятор применяет устранение копирования и перемещение. Сначала пиши ясный код и измеряй реальные проблемы.

### Что выражает `unique_ptr`?

Единственное владение динамическим объектом с автоматическим уничтожением.

### Почему `unique_ptr` нельзя копировать?

Копирование создало бы двух единственных владельцев. Владение передаётся перемещением.

### Когда нужен `shared_ptr`?

Когда несколько независимых владельцев действительно должны совместно определять срок жизни одного объекта.

### Зачем нужен `weak_ptr`?

Для невладеющего наблюдения за объектом под `shared_ptr`, в том числе для разрыва циклов совместного владения.

### Делает ли `shared_ptr` сам объект потокобезопасным?

Нет. Безопасно синхронизируется управление счётчиком, но доступ к состоянию объекта требует собственной синхронизации.

### Почему у полиморфного базового класса нужен виртуальный деструктор?

Чтобы удаление производного объекта через указатель на базовый тип вызвало правильную цепочку деструкторов.
