# Глава 11. Ошибки, контракты и исключения

## Зачем нужна эта глава

Надёжная программа отличается от демонстрационного примера не тем, что в ней «никогда не бывает ошибок». Она умеет отличать разные виды нештатных ситуаций и реагировать на них осмысленно.

Представь функцию, которая вычисляет среднее значение измерений. Пустой набор может означать нормальную ситуацию «измерений пока нет». А отрицательная частота дискретизации, возможно, означает ошибку в программе или конфигурации. Если свалить оба случая в одно число `0.0`, вызывающий код уже не сможет понять, что произошло.

В этой главе ты научишься сначала формулировать контракт, а потом выбирать способ сообщения об ошибке. Это важнее, чем запомнить синтаксис `throw` и `catch`.

## Что ты будешь уметь после главы

Ты сможешь:

- различать ошибку компиляции, ошибку линковки, ошибку времени выполнения и нарушение контракта;
- формулировать предусловия, постусловия и инварианты;
- выбирать между обычным возвращаемым значением, `std::optional`, исключением и `assert`;
- бросать исключения подходящего типа и перехватывать их по `const`-ссылке;
- понимать, почему RAII делает выход по исключению безопаснее;
- сохранять объект в корректном состоянии, даже если операция завершилась ошибкой;
- не использовать исключения и `assert` как взаимозаменяемые средства.

## 1. Ошибки бывают разными

Полезно сначала определить слой, на котором возникла проблема.

### Ошибка компиляции

Компилятор не смог преобразовать исходный текст в объектный код. Например, имя не объявлено, типы несовместимы или нарушен синтаксис.

```text
error: use of undeclared identifier 'sampleRate'
```

Такая ошибка не попадает в `try`/`catch`: программа ещё не существует как исполняемый файл.

### Ошибка линковки

Каждый `.cpp` уже скомпилирован, но линкер не смог собрать из объектных файлов программу. Частый пример: функция объявлена и вызвана, но её определение не попало в цель сборки.

```text
undefined reference to `calculatePower(...)`
```

Исключения здесь тоже не помогают. Нужно проверить определения функций и конфигурацию сборки.

### Ошибка времени выполнения

Программа запустилась, но во время работы произошло нештатное событие: файл не найден, входная строка имеет неверный формат, ресурс недоступен, нарушено допустимое значение параметра.

Часть таких ситуаций ожидаема. Пользователь вполне может указать несуществующий файл. Это не обязательно дефект программы — программа должна сообщить о проблеме.

### Дефект программы

Выход за границы массива, висячая ссылка, деление целого числа на ноль и использование неинициализированного значения — не «обычные ошибки пользователя». Это дефекты реализации. Некоторые из них приводят к неопределённому поведению: стандарт C++ больше не обещает программе никакого конкретного результата.

Исключение не превращает неопределённое поведение в безопасное. Такие дефекты ищут тестами, предупреждениями, отладчиком и санитайзерами.

## 2. Контракт функции или класса

Контракт отвечает на вопрос: что обещают друг другу вызывающий код и реализация?

### Предусловие

То, что должно быть истинно до вызова.

Пример: функция вычисления RMS требует непустой набор конечных чисел.

### Постусловие

То, что функция гарантирует после успешного завершения.

Пример: результат RMS неотрицателен.

### Инвариант

Условие, которое должно оставаться истинным для корректно существующего объекта.

Пример: у диапазона частот нижняя граница не превосходит верхнюю, а обе границы конечны.

Хороший интерфейс делает контракт видимым через типы и имена. Например, `std::optional<double>` честнее, чем условное значение `-1.0`, если результат иногда отсутствует.

## 3. Четыре основных способа сообщить о проблеме

### Обычное возвращаемое значение

Используй его, если все исходы принадлежат обычной логике функции. Например, предикат `contains()` возвращает `true` или `false`: отсутствие элемента не является ошибкой.

### `std::optional<T>`

`std::optional<T>` означает: корректный результат типа `T` либо отсутствие результата. Он подходит, когда отсутствие ожидаемо и не требует подробного объяснения причины.

```cpp
std::optional<double> mean(std::span<const double> values);
```

Если причин отказа несколько и вызывающему коду важно их различать, одного `optional` уже недостаточно. Тогда нужен отдельный тип результата, `std::variant`, код ошибки или исключение. В C++23 для этого появился `std::expected`, но эта книга использует C++20 и не зависит от него.

### Исключение

Исключение подходит, когда функция не может выполнить обещанную операцию, а локально исправить ситуацию нельзя. Исключение переносит управление к ближайшему подходящему обработчику.

```cpp
throw std::invalid_argument("sample rate must be positive");
```

Исключение не должно заменять каждую обычную ветку `if`. Например, поиск элемента в коллекции обычно не требует исключения при отсутствии элемента.

### `assert`

`assert(condition)` проверяет предположение разработчика. Это средство обнаружения дефектов, а не обработки пользовательского ввода.

```cpp
#include <cassert>

double square(double value) {
    assert(value >= 0.0); // Уместно только если это внутреннее обещание программы.
    return value * value;
}
```

При определённом макросе `NDEBUG` стандартный `assert` полностью отключается. Поэтому нельзя писать так:

```cpp
assert(readConfiguration()); // Плохо: важный вызов исчезнет в Release-сборке.
```

Выражение внутри `assert` не должно выполнять необходимую работу или изменять состояние программы.

## 4. Как устроены исключения

Исключение бросается оператором `throw`:

```cpp
if (sampleRate <= 0.0) {
    throw std::invalid_argument("sample rate must be positive");
}
```

Код, способный осмысленно отреагировать, использует `try` и `catch`:

```cpp
try {
    runModel();
} catch (const std::invalid_argument& error) {
    std::cerr << "Configuration error: " << error.what() << '\n';
}
```

Перехватывай стандартные исключения по `const`-ссылке. Передача по значению может скопировать исключение и потерять информацию производного типа.

Сначала размещают более конкретные обработчики, затем более общие:

```cpp
try {
    runModel();
} catch (const std::invalid_argument& error) {
    // Конкретная реакция на неверный аргумент.
} catch (const std::exception& error) {
    // Общий запасной обработчик стандартных исключений.
}
```

Не лови исключение только ради того, чтобы ничего не сделать:

```cpp
try {
    runModel();
} catch (...) {
    // Ошибка потеряна, программа делает вид, что всё хорошо.
}
```

Если обработчик не может исправить ситуацию, он может добавить контекст и бросить исключение дальше либо позволить ему пройти без перехвата.

## 5. RAII и раскрутка стека

Когда исключение покидает функцию, локальные объекты этой функции уничтожаются в обратном порядке. Этот процесс называют раскруткой стека. Деструкторы локальных объектов освобождают принадлежащие им ресурсы.

Поэтому такой код безопасен:

```cpp
void processFile(const std::string& path) {
    std::ifstream input(path);
    if (!input) {
        throw std::runtime_error("cannot open " + path);
    }

    // Если следующая операция бросит исключение,
    // деструктор input всё равно закроет файл.
    process(input);
}
```

Тебе не нужен отдельный `close()` в каждом пути выхода. Это и есть практическая сила RAII.

Деструктор, освобождающий ресурс, обычно не должен бросать исключение. Во время раскрутки стека уже может обрабатываться другое исключение; второе исключение из деструктора способно завершить программу.

## 6. Гарантии при исключениях

При проектировании изменяющей операции полезно спросить, в каком состоянии останется объект при ошибке.

- **Базовая гарантия:** объект остаётся корректным, ресурсы не утекают, но его значение могло измениться.
- **Сильная гарантия:** операция либо полностью успешна, либо наблюдаемое состояние остаётся прежним.
- **Гарантия отсутствия исключений:** операция обещает не бросать; это обозначают `noexcept`, только если обещание действительно можно выполнить.

Один из простых способов получить сильную гарантию — сначала построить и проверить временный результат, а затем опубликовать его короткой операцией.

Не добавляй `noexcept` «для скорости». Если функция с `noexcept` всё же выпустит исключение наружу, будет вызван `std::terminate`.

## 7. Разобранный пример: ожидаемое отсутствие результата

Функция среднего значения для пустого набора не обязана считать пустоту аварией. Вернём `std::nullopt`.

```cpp
#include <iostream>
#include <numeric>
#include <optional>
#include <span>
#include <vector>

std::optional<double> mean(std::span<const double> values) {
    if (values.empty()) {
        return std::nullopt;
    }

    const double sum = std::accumulate(values.begin(), values.end(), 0.0);
    return sum / static_cast<double>(values.size());
}

void printMean(std::span<const double> values) {
    const std::optional<double> result = mean(values);
    if (result) {
        std::cout << "Mean: " << *result << '\n';
    } else {
        std::cout << "There are no samples\n";
    }
}

int main() {
    const std::vector<double> samples{1.0, 2.0, 6.0};
    const std::vector<double> empty;

    printMean(samples);
    printMean(empty);
}
```

Сборка:

```bash
clang++ -std=c++20 -Wall -Wextra -Wpedantic mean.cpp -o mean
./mean
```

Здесь `optional` сообщает ровно один факт: среднего нет. Исключение было бы неудобно, если пустой набор регулярно возникает до прихода первых измерений.

## 8. Разобранный пример: проверка до изменения состояния

Следующий класс хранит таблицу коэффициентов. Пустая таблица и неконечные значения нарушают её инвариант. Метод сначала проверяет новый вектор и только потом заменяет старый.

```cpp
#include <cmath>
#include <iostream>
#include <stdexcept>
#include <utility>
#include <vector>

class GainTable {
public:
    explicit GainTable(std::vector<double> gains) {
        validate(gains);
        gains_ = std::move(gains);
    }

    void replace(std::vector<double> candidate) {
        validate(candidate);          // Может бросить. gains_ ещё не изменён.
        gains_ = std::move(candidate);
    }

    double at(std::size_t index) const {
        return gains_.at(index);      // std::vector::at проверяет границу.
    }

    std::size_t size() const noexcept {
        return gains_.size();
    }

private:
    static void validate(const std::vector<double>& gains) {
        if (gains.empty()) {
            throw std::invalid_argument("gain table must not be empty");
        }

        for (const double gain : gains) {
            if (!std::isfinite(gain)) {
                throw std::invalid_argument("every gain must be finite");
            }
        }
    }

    std::vector<double> gains_;
};

int main() {
    GainTable table({1.0, 0.5});

    try {
        table.replace({2.0, std::nan("")});
    } catch (const std::invalid_argument& error) {
        std::cout << "Rejected update: " << error.what() << '\n';
    }

    std::cout << "First old value is still " << table.at(0) << '\n';
}
```

После неудачного `replace()` таблица по-прежнему содержит `{1.0, 0.5}`. Временный параметр `candidate` уничтожится автоматически. Ручного освобождения памяти нет.

## Связь с MATLAB

В MATLAB тебе знакомы `error`, `warning`, `assert` и `try/catch`. Главная идея контракта остаётся той же, но C++ добавляет несколько важных особенностей:

- многие ошибки типов обнаруживаются ещё компилятором;
- ошибки линковки образуют отдельный класс проблем;
- неопределённое поведение может не породить аккуратное исключение;
- локальные RAII-объекты освобождают ресурсы во время раскрутки стека;
- тип результата может явно кодировать отсутствие значения;
- деструктор и владение ресурсом являются частью контракта типа.

Не пытайся воспроизвести MATLAB-стиль, где любая проблема превращается в `error(...)`. В C++ ожидаемое отсутствие значения часто лучше выразить типом, а дефект памяти искать санитайзером.

## Типичные ошибки

1. **Возвращать `-1`, `0` или пустую строку без документированного смысла.** Такое значение легко спутать с нормальным результатом.
2. **Использовать `optional`, когда вызывающему коду нужна причина отказа.** `nullopt` не хранит объяснение.
3. **Бросать исключение для обычного результата поиска.** Это усложняет основной путь выполнения.
4. **Проверять пользовательский ввод через `assert`.** В Release-сборке проверка может исчезнуть.
5. **Выполнять полезную работу внутри `assert`.** Вместе с проверкой исчезнет и работа.
6. **Ловить исключение по значению.** Используй `const std::exception&` или более конкретную `const`-ссылку.
7. **Ловить всё и молчать.** Ошибка теряется, а программа продолжает работу с сомнительным состоянием.
8. **Менять объект постепенно, а проверять в конце.** При исключении объект может остаться наполовину обновлённым.
9. **Бросать исключение из деструктора.** Это особенно опасно при раскрутке стека.
10. **Помечать функцию `noexcept` без доказательства.** Нарушение обещания завершит программу.
11. **Надеяться, что `try/catch` поймает выход за границы через `operator[]`.** У такого доступа нет обязательной проверки.
12. **Терять контекст.** Сообщение `"bad value"` хуже, чем `"sample rate must be positive"`.

## Упражнения

### Уровень 1. Безопасное деление

Напиши функцию:

```cpp
std::optional<double> safeDivide(double numerator, double denominator);
```

Она должна возвращать `std::nullopt`, если знаменатель равен нулю, и результат в остальных случаях. Добавь примеры для положительного, отрицательного и нулевого знаменателя. Затем реши, нужно ли отдельно отвергать `NaN` и бесконечность, и запиши контракт словами.

<details>
<summary>Подсказка</summary>

Начни с явного `if`. Не используй исключение, пока отсутствие результата является ожидаемым исходом. Для проверки конечности существует `std::isfinite` из `<cmath>`.

</details>

### Уровень 2. Конфигурация модели

Создай класс `ModelConfig` с полями `sampleRate` и `frameCount`. Требования:

- `sampleRate` — конечное положительное число;
- `frameCount` — положительное целое число;
- после создания объект всегда корректен;
- изменить поля напрямую нельзя;
- некорректный конструктор бросает `std::invalid_argument` с понятным сообщением.

Напиши небольшую программу, которая создаёт корректный объект и отдельно обрабатывает две ошибки.

<details>
<summary>Подсказка</summary>

Проверяй параметры в теле конструктора до того, как объект станет доступен вызывающему коду. Поля сделай `private`. Для чтения достаточно `const`-методов без сеттеров.

</details>

### Уровень 3. Атомарное обновление

Расширь `ModelConfig` методом, который принимает сразу новую частоту и новое число кадров. Если хотя бы одно значение некорректно, оба старых значения должны сохраниться. Добавь тест или проверки в `main`, демонстрирующие сильную гарантию.

Затем ответь письменно: почему два независимых сеттера затрудняют выполнение этого контракта?

<details>
<summary>Подсказка</summary>

Сначала проверь оба аргумента, не меняя поля. Только после успешной проверки присвой оба значения. Ещё один вариант — создать временный корректный объект и затем обменять состояние.

</details>

## Вопросы для самопроверки

1. Чем ожидаемое отсутствие результата отличается от нарушения контракта?
2. Почему исключение нельзя поймать вокруг ошибки компиляции?
3. Когда `std::optional` недостаточно информативен?
4. Почему `assert` не подходит для проверки пути к файлу, введённого пользователем?
5. Как правильно перехватывать стандартное исключение?
6. Что происходит с локальными RAII-объектами при выходе по исключению?
7. Что означает сильная гарантия?
8. Что произойдёт, если исключение покинет функцию с `noexcept`?
9. Почему `operator[]` не следует считать механизмом обработки ошибки границ?
10. Должна ли функция ловить исключение, если она не умеет осмысленно восстановиться?

<details>
<summary>Краткие ответы</summary>

1. Отсутствие может быть нормальным исходом; нарушение контракта означает, что обещанная операция вызвана или реализована неверно.
2. Исполняемая программа ещё не построена.
3. Когда нужно различить несколько причин отказа или сохранить подробности.
4. `assert` может быть отключён и предназначен для предположений разработчика.
5. По `const`-ссылке, начиная с наиболее конкретного типа.
6. Они уничтожаются в обратном порядке, освобождая ресурсы.
7. Неудачная операция не меняет наблюдаемое состояние объекта.
8. Будет вызван `std::terminate`.
9. Он обычно не проверяет границы и выход за них может стать неопределённым поведением.
10. Обычно нет; исключение следует пропустить к уровню, который знает, что делать.

</details>
