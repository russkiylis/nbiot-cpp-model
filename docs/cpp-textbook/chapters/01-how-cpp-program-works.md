# Глава 1. Как работает программа на C++

## Зачем тебе нужна эта тема

В MATLAB ты можешь открыть скрипт, нажать Run и сразу увидеть результат. Между текстом программы и выполнением многое скрыто средой. В C++ этот путь нужно понимать явно: исходный код компилируется, отдельные части связываются вместе, и только затем запускается готовая программа.

Это не формальность. Понимание пути от `.cpp` до исполняемого файла помогает различать:

- ошибку компиляции;
- ошибку линковки;
- ошибку во время выполнения;
- логическую ошибку;
- проблему настройки сборки.

Без этой модели новичок часто пытается исправлять не тот файл или бесконечно нажимает Build, не читая первую полезную диагностику. После главы ты будешь понимать, что именно делает каждый инструмент и на каком этапе искать проблему.

## Результаты обучения

После главы ты сможешь:

- объяснить путь от исходного файла до запущенной программы;
- назвать роли препроцессора, компилятора и линкера;
- написать минимальную программу с `main`;
- собрать один `.cpp` вручную в режиме C++20;
- понимать назначение `#include`;
- различать объявление и определение функции;
- собрать многофайловую программу;
- использовать простой `CMakeLists.txt`;
- выполнить чистую сборку вне каталога исходников;
- отличить предупреждение от ошибки;
- классифицировать основные виды неисправностей.

## 1. Исходный код ещё не является программой

Файл `main.cpp` — обычный текст. Процессор не выполняет строки C++ напрямую. Сначала инструменты преобразуют исходный код в машинные инструкции.

Упрощённый путь выглядит так:

```text
main.cpp ──┐
           ├─> компиляция ─> объектные файлы ─> линковка ─> исполняемая программа
math.cpp ──┘
```

Разберём этапы.

### Этап 1. Препроцессор

До основной компиляции обрабатываются директивы, начинающиеся с `#`:

```cpp
#include <iostream>
```

Для начальной модели можно считать, что `#include` подставляет содержимое нужного заголовка в текущую единицу трансляции. Реальные детали сложнее, но пока этой модели достаточно.

Препроцессор также умеет работать с макросами и условной компиляцией. Не спеши использовать их: для большинства обычных констант и функций в современном C++ есть более безопасные языковые средства.

### Этап 2. Компилятор

Компилятор разбирает каждую единицу трансляции отдельно:

- проверяет синтаксис;
- проверяет типы;
- проверяет, что используемые имена объявлены;
- создаёт объектный файл с машинным кодом и служебной информацией.

Обычно один `.cpp` после обработки включённых заголовков образует одну единицу трансляции.

Если написать имя несуществующей переменной или передать строку туда, где ожидается число, ошибка чаще всего возникнет на этом этапе.

### Этап 3. Линкер

Линкер получает объектные файлы и библиотеки. Он связывает вызовы с конкретными определениями функций и создаёт исполняемый файл.

Например, `main.cpp` знает из объявления, что существует функция `square`, а её тело находится в `math.cpp`. Компилятор обработает файлы отдельно, а линкер соединит вызов с реализацией.

Если функция объявлена и вызвана, но её определение не попало в сборку, исходный файл может успешно скомпилироваться, а линкер сообщит о неопределённом символе.

### Этап 4. Запуск

Операционная система загружает готовый исполняемый файл и передаёт управление функции `main`. Во время выполнения могут появиться другие проблемы: неправильный индекс, деление на ноль в неподходящем типе, неверный файл, некорректный ввод или нарушенная логика.

## 2. Минимальная программа

```cpp
#include <iostream>

int main()
{
    std::cout << "Hello, C++!\n";
    return 0;
}
```

Разберём каждую часть.

### `#include <iostream>`

Заголовок объявляет средства потокового ввода и вывода, включая `std::cout`.

### `int main()`

`main` — точка входа обычной консольной C++-программы. Операционная система начинает выполнение с неё.

Тип результата `int` используется как код завершения:

- `0` обычно означает успех;
- ненулевое значение сообщает об ошибке вызывающей среде.

До конца `main` можно дойти без явного `return 0`, но на первом этапе лучше писать его явно, чтобы видеть контракт.

### Фигурные скобки

`{` и `}` задают тело функции и область видимости.

### `std::cout`

Это стандартный поток вывода. Префикс `std::` означает, что имя находится в пространстве имён стандартной библиотеки.

Не добавляй глобальное `using namespace std;`, особенно в заголовках. Явный `std::` помогает видеть происхождение имени и предотвращает конфликты.

### `\n`

Это символ новой строки. Он переводит последующий вывод на следующую строку.

### Точка с запятой

Большинство простых инструкций C++ завершается `;`.

## 3. Ручная сборка одного файла

Если файл называется `main.cpp`, общая форма команды выглядит так:

```bash
c++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp -o hello
```

Здесь:

- `c++` запускает доступный C++-компилятор через общее имя драйвера;
- `-std=c++20` выбирает стандарт C++20;
- `-Wall -Wextra -Wpedantic` включает полезные предупреждения в распространённых компиляторах;
- `main.cpp` — исходный файл;
- `-o hello` задаёт имя результата.

Запуск на macOS или Linux:

```bash
./hello
```

Если команда компилятора в твоей системе называется иначе, принцип остаётся тем же: выбрать C++20, передать исходники и задать выходной файл.

## 4. Предупреждения — это не фон

Ошибка останавливает сборку. Предупреждение сообщает о подозрительном коде, который компилятор всё же способен преобразовать.

Пример:

```cpp
int main()
{
    int unused{42};
    return 0;
}
```

При включённых предупреждениях компилятор может сообщить, что `unused` не используется.

Не следует бездумно подавлять предупреждения. Сначала пойми причину. В учебных исходниках разумная цель — отсутствие предупреждений в твоём собственном коде.

При этом предупреждение сторонней библиотеки и предупреждение твоего файла — разные ситуации. Не изменяй чужой код только ради тишины, пока не установил источник.

## 5. Объявление и определение

Объявление функции сообщает её имя и типы:

```cpp
double square(double value);
```

Определение содержит тело:

```cpp
double square(double value)
{
    return value * value;
}
```

Компилятору достаточно объявления, чтобы проверить вызов. Но линкеру потребуется одно подходящее определение.

Это различие объясняет типичную ситуацию:

1. `main.cpp` включает заголовок с объявлением;
2. вызов компилируется;
3. файл с определением забыли добавить в сборку;
4. линкер не может найти тело функции.

## 6. Заголовочные и исходные файлы

Обычное небольшое разделение:

```text
project/
├── CMakeLists.txt
├── include/
│   └── temperature.h
└── src/
    ├── main.cpp
    └── temperature.cpp
```

В заголовке находится интерфейс:

```cpp
#pragma once

double celsiusToFahrenheit(double celsius);
```

В `.cpp` — реализация:

```cpp
#include "temperature.h"

double celsiusToFahrenheit(double celsius)
{
    return celsius * 9.0 / 5.0 + 32.0;
}
```

Файл реализации включает собственный заголовок. Это помогает компилятору проверить, что объявление и определение согласованы.

`#pragma once` защищает заголовок от повторного включения в одну единицу трансляции. Существуют и традиционные include guards; на первом этапе достаточно уверенно использовать один механизм, принятый в проекте.

Заголовок должен содержать то, что нужно пользователю интерфейса. Внутренние детали реализации без необходимости туда не помещают.

## 7. Что делает CMake

CMake — не компилятор. Это инструмент, который описывает цели проекта и создаёт систему сборки для доступного окружения.

Минимальный `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)

project(temperature_app LANGUAGES CXX)

add_executable(temperature_app
    src/main.cpp
    src/temperature.cpp
)

target_include_directories(temperature_app PRIVATE include)
target_compile_features(temperature_app PRIVATE cxx_std_20)
```

Здесь:

- создаётся проект с языком C++;
- объявляется исполняемая цель `temperature_app`;
- перечисляются исходные файлы цели;
- указывается каталог заголовков;
- требуется стандарт C++20.

Команды сборки:

```bash
cmake -S . -B build
cmake --build build
```

`-S .` означает каталог исходников, `-B build` — отдельный каталог сборки.

Такой подход называется out-of-source build: временные файлы сборки не смешиваются с исходным кодом.

Чистая проверка:

1. используй новый пустой каталог сборки;
2. снова выполни конфигурацию;
3. собери проект;
4. запусти результат.

Если проект работает только со старым `build`, возможно, он случайно зависит от устаревших файлов.

## 8. Debug и Release

Обычно используют как минимум два режима:

- **Debug** — удобен для отладки, содержит дополнительную информацию и мало оптимизируется;
- **Release** — оптимизирован для выполнения и хуже подходит для пошаговой отладки.

Для генераторов с одним режимом пример конфигурации Debug:

```bash
cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug
```

Не сравнивай производительность алгоритмов по Debug-сборке. И не пытайся отлаживать сложную проблему только в сильно оптимизированной Release-сборке, если она воспроизводится в Debug.

## 9. Четыре класса проблем

### Ошибка компиляции

Пример:

```cpp
int main()
{
    std::cout << unknownName << '\n';
}
```

Имя не объявлено. Компилятор не сможет создать объектный файл.

Другие причины:

- пропущена `;`;
- неверный тип аргумента;
- забытый `#include`;
- несовпадающие фигурные скобки.

### Ошибка линковки

```cpp
double square(double value);

int main()
{
    return square(2.0) > 0.0 ? 0 : 1;
}
```

Код содержит объявление, поэтому вызов можно скомпилировать. Но определения `square` нет, и линкер сообщит об неопределённом символе.

Другой вариант — определение существует, но соответствующий `.cpp` не добавлен в цель.

### Ошибка времени выполнения

Программа успешно собрана, но во время работы получает неверное состояние: не может открыть файл, обращается за границу контейнера или нарушает требуемое предусловие.

### Логическая ошибка

Программа запускается и не падает, но выдаёт неправильный ответ:

```cpp
double rectangleArea(double width, double height)
{
    return width + height; // должно быть умножение
}
```

Компилятор не знает математику твоей задачи. Логические ошибки обнаруживаются проверками, тестами и анализом контракта.

## 10. Как читать диагностику

Сообщение компилятора может быть длинным, особенно когда одна ошибка вызывает много последующих. Рабочий порядок:

1. найди первое сообщение, относящееся к твоему исходному файлу;
2. прочитай тип: `error`, `warning`, иногда `note`;
3. посмотри файл и строку;
4. прочитай, что ожидалось и что было получено;
5. исправь одну первичную причину;
6. собери заново.

Не начинай с последней строки длинного вывода. Она часто только сообщает, что вся команда завершилась неуспешно.

При ошибке линковки проверь:

- есть ли определение функции;
- совпадает ли его сигнатура с объявлением;
- добавлен ли нужный `.cpp` или библиотека в target;
- не определена ли функция дважды.

## 11. Отличия от MATLAB

### Изменение исходника требует новой сборки

После редактирования `.cpp` нужно снова получить актуальный исполняемый файл. Система сборки обычно пересоберёт только изменившиеся части.

### Нет общего workspace скрипта

Обычная C++-программа начинает работу с `main`, а переменные имеют конкретные области видимости и время жизни.

### Файлы компилируются отдельно

Один `.cpp` не «видит» содержимое другого автоматически. Общий интерфейс объявляется в заголовке, а связь определений выполняет линкер.

### Типы проверяются до запуска

Многие ошибки, которые в MATLAB проявились бы при выполнении определённой строки, C++ обнаруживает при компиляции.

### CMake описывает цели

Вместо запуска отдельного скрипта проект может содержать библиотеку, приложение и тесты. CMake сообщает, какие исходники относятся к каждой цели и как цели связаны.

### Сборка и запуск — разные действия

Успешная сборка доказывает только то, что получен исполняемый файл. Она не доказывает правильность результата.

## 12. Разобранный пример 1: один файл

Создай `main.cpp`:

```cpp
#include <iostream>

double celsiusToFahrenheit(double celsius)
{
    return celsius * 9.0 / 5.0 + 32.0;
}

int main()
{
    const double celsius{25.0};
    const double fahrenheit{celsiusToFahrenheit(celsius)};

    std::cout << celsius << " C = "
              << fahrenheit << " F\n";
    return 0;
}
```

Сборка и запуск:

```bash
c++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp -o temperature
./temperature
```

Разбор:

- `iostream` нужен для `std::cout`;
- функция определена до `main`, поэтому отдельное предварительное объявление не требуется;
- литералы `9.0` и `5.0` задают вещественное деление;
- `const` сообщает, что вычисленные переменные дальше не меняются;
- вычисление отделено от вывода;
- `return 0` сообщает об успешном завершении.

## 13. Разобранный пример 2: многофайловая сборка

Структура:

```text
temperature-project/
├── CMakeLists.txt
├── include/
│   └── temperature.h
└── src/
    ├── main.cpp
    └── temperature.cpp
```

`include/temperature.h`:

```cpp
#pragma once

double celsiusToFahrenheit(double celsius);
bool isComfortable(double celsius);
```

`src/temperature.cpp`:

```cpp
#include "temperature.h"

double celsiusToFahrenheit(double celsius)
{
    return celsius * 9.0 / 5.0 + 32.0;
}

bool isComfortable(double celsius)
{
    return celsius >= 20.0 && celsius <= 24.0;
}
```

`src/main.cpp`:

```cpp
#include "temperature.h"

#include <iostream>

int main()
{
    const double roomTemperature{22.5};

    std::cout << "Fahrenheit: "
              << celsiusToFahrenheit(roomTemperature) << '\n';
    std::cout << "Comfortable: "
              << std::boolalpha
              << isComfortable(roomTemperature) << '\n';
    return 0;
}
```

`CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)

project(temperature_app LANGUAGES CXX)

add_executable(temperature_app
    src/main.cpp
    src/temperature.cpp
)

target_include_directories(temperature_app PRIVATE include)
target_compile_features(temperature_app PRIVATE cxx_std_20)
```

Сборка:

```bash
cmake -S . -B build
cmake --build build
```

Разбор:

- заголовок содержит общий интерфейс;
- оба `.cpp` включают нужный заголовок;
- реализация находится только в `temperature.cpp`;
- CMake target перечисляет оба исходных файла;
- каталог `include` добавлен к путям поиска заголовков;
- если удалить `src/temperature.cpp` из `add_executable`, вызовы скомпилируются, но линковка завершится ошибкой;
- если изменить объявление, но не определение, компилятор или линкер обнаружит несоответствие.

## 14. Типичные ошибки

### Ошибка 1. CMake принимают за компилятор

CMake описывает и генерирует сборку. Машинный код создаёт выбранный C++-компилятор, а готовый файл собирает линкер.

### Ошибка 2. Запускается старый executable

Исходник изменён, но сборка не выполнена или запускается файл из другого каталога. Всегда понимай, какой путь ты запускаешь.

### Ошибка 3. В target забыли `.cpp`

Заголовок найден, вызов скомпилирован, но определение не попало на линковку.

### Ошибка 4. Определение обычной функции положили в заголовок без необходимости

При включении в несколько `.cpp` можно получить несколько определений. Пока держи объявления в `.h`, а обычные определения в `.cpp`.

### Ошибка 5. Используется `using namespace std;` в заголовке

Так чужому коду навязываются имена и создаются конфликты. Используй `std::`.

### Ошибка 6. Читается последняя, а не первая полезная диагностика

Одна пропущенная скобка может вызвать десятки последующих сообщений. Исправляй первичную ошибку сверху.

### Ошибка 7. Предупреждения игнорируются

Предупреждение нередко указывает на реальную логическую проблему: неиспользуемое значение, подозрительное преобразование или неверное условие.

### Ошибка 8. Успешная сборка считается доказательством правильности

Компилятор не знает ожидаемую формулу. Нужны проверки и тесты.

### Ошибка 9. Служебные файлы сборки кладутся рядом с исходниками

Используй отдельный каталог `build`, чтобы проект было легко очистить и воспроизвести.

## 15. Упражнения

### Уровень 1. Один файл и диагностика

1. Создай программу, которая переводит километры в метры.
2. Собери её как C++20 с предупреждениями.
3. Намеренно удали `;`, прочитай первую ошибку и восстанови код.
4. Намеренно напиши неправильное имя переменной и классифицируй ошибку.
5. Измени формулу на неправильную, собери программу и объясни, почему компилятор не возражает.

<summary>Подсказка к уровню 1</summary>

Сделай отдельную функцию `double kilometersToMeters(double kilometers)`. Ошибка в имени или `;` относится к компиляции. Неверный множитель — логическая ошибка: типы и синтаксис остаются допустимыми.

</details>

### Уровень 2. Разделение файлов

1. Создай `geometry.h`, `geometry.cpp` и `main.cpp`.
2. Объяви и определи функции площади прямоугольника и длины окружности.
3. Собери все файлы одной командой компилятора.
4. Затем убери `geometry.cpp` из команды и исследуй ошибку линковки.
5. Верни файл, но намеренно измени тип одного параметра только в определении. Прочитай диагностику.

<details>
<summary>Подсказка к уровню 2</summary>

При ручной сборке передай компилятору оба `.cpp`: `c++ ... main.cpp geometry.cpp -o geometry_app`. В `geometry.cpp` первым включи `geometry.h`, чтобы несогласованная сигнатура обнаруживалась ближе к источнику.

</details>

### Уровень 3. Самостоятельный CMake-проект

Создай проект с такой структурой:

```text
unit-converter/
├── CMakeLists.txt
├── include/
│   └── converter.h
└── src/
    ├── converter.cpp
    └── main.cpp
```

Требования:

- C++20;
- исполняемая цель `unit_converter`;
- минимум три функции пересчёта;
- `main` только выбирает данные, вызывает функции и печатает результаты;
- сборка выполняется в отдельном каталоге;
- после успешной сборки удали каталог сборки и воспроизведи её с нуля;
- создай по одному примеру ошибки компиляции, линковки и логики, затем исправь их;
- запиши своими словами, как ты отличил ошибки.

<details>
<summary>Подсказка к уровню 3</summary>

Начни с минимального `project`, `add_executable`, `target_include_directories` и `target_compile_features`. Добавляй каждую строку только после того, как можешь объяснить её назначение. Ошибку линковки удобно получить, временно убрав `converter.cpp` из списка исходников цели.

</details>

## 16. Вопросы для самопроверки

### 1. Выполняет ли процессор текст `.cpp` напрямую?

Нет. Исходный код сначала компилируется и связывается в исполняемую программу.

### 2. Что делает компилятор?

Проверяет синтаксис и типы каждой единицы трансляции и создаёт объектный код.

### 3. Что делает линкер?

Связывает определения из объектных файлов и библиотек с их использованиями и создаёт исполняемый файл.

### 4. Для чего нужен `#include`?

Чтобы сделать объявления из заголовка доступными текущей единице трансляции.

### 5. Чем объявление отличается от определения?

Объявление сообщает интерфейс, определение содержит реализацию и создаваемую сущность.

### 6. Почему вызов может скомпилироваться, но не слинковаться?

Компилятор видел объявление, но линкер не получил подходящее определение.

### 7. Является ли CMake компилятором?

Нет. Он описывает и генерирует процесс сборки, который использует компилятор и линкер.

### 8. Зачем отдельный каталог `build`?

Чтобы не смешивать исходники со служебными файлами и уметь воспроизвести чистую сборку.

### 9. Что означает код возврата `0` из `main`?

Обычно успешное завершение программы.

### 10. Доказывает ли успешная компиляция правильность формулы?

Нет. Компилятор проверяет язык и типы, но не предметный смысл вычисления.

### 11. С какого сообщения начинать разбор длинной диагностики?

С первого содержательного сообщения, относящегося к твоему исходному файлу.

### 12. Чем Debug отличается от Release?

Debug удобнее для отладки и обычно почти не оптимизирован. Release оптимизирован для выполнения.
