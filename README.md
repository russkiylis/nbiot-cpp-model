# Архитектурный каркас модели Downlink NB-IoT на C++

Этот репозиторий содержит учебную C++20-модель нисходящего канала NB-IoT. В
проект добавлен архитектурный каркас, похожий по общей идее на MATLAB-проект
`nbiot-downlink-model`:

```text
main.cpp -> DownlinkManager -> Frame -> Subframe
                                  \-> ResourceGrid
```

Главная задача каркаса — показать, **как разделить ответственность между
классами**, организовать владение объектами и подготовить места для будущих
алгоритмов.

> [!IMPORTANT]
> Новый архитектурный слой пока **не генерирует физический сигнал**. Методы
> размещения NPBCH, NPSS, NSSS, NPDSCH, NPDCCH и NRS являются честными
> заглушками и выбрасывают `std::logic_error`. Рабочим результатом текущего
> основного приложения является только построенная топология кадров и
> сабфреймов.

В репозитории также остались ранее написанные алгоритмические классы: CRC,
TBCC, Rate Matcher, Scrambler, QPSK, генераторы NPSS/NSSS и другие. Они
собираются в общей библиотеке, но **ещё не подключены** к новому менеджеру и
сабфреймам.

Подробное объяснение классов и диаграммы находятся в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Что уже есть

- `nbiot::DownlinkManager`, создаваемый из `main.cpp`;
- конфигурация `nbiot::ModelConfig`;
- кадр `nbiot::Frame`, содержащий ровно десять сабфреймов;
- абстрактный базовый класс `nbiot::Subframe`;
- шесть конкретных типов сабфреймов:
  `NpbchSubframe`, `NpssSubframe`, `NsssSubframe`, `NpdschSubframe`,
  `NpdcchSubframe`, `EmptySubframe`;
- фабрика `nbiot::SubframeFactory`;
- типизированная ресурсная сетка `nbiot::ResourceGrid`;
- отдельная будущая стадия наложения опорного сигнала
  `nbiot::NrsOverlay`;
- русскоязычные Doxygen-комментарии к новому публичному API;
- архитектурные тесты и smoke-тест основного приложения;
- отдельное демонстрационное приложение со старым пайплайном.

## Что пока не реализовано

- формулы и последовательности NPBCH, NPSS, NSSS, NPDSCH и NPDCCH внутри
  нового архитектурного слоя;
- размещение каналов и сигналов по ресурсным элементам;
- наложение NRS;
- планировщики NPDSCH/NPDCCH;
- SIB1-NB;
- OFDM-модуляция нового слоя;
- визуализация сетки и сигнала.

Такое ограничение сделано намеренно: сначала строится понятный «скелет», а
затем каждый алгоритм можно добавлять отдельно, не превращая `main.cpp` или
менеджер в один большой файл.

## Быстрый старт

### Требования

- компилятор с поддержкой C++20;
- CMake 3.20 или новее;
- Git и доступ к интернету для первой загрузки GoogleTest, если тесты
  включены.

### Сборка и запуск основного приложения

Из корня репозитория выполните:

```bash
cmake -S . -B build
cmake --build build --target NBIoT_CPP_Model
./build/NBIoT_CPP_Model
```

На Windows при использовании многоконфигурационного генератора исполняемый
файл может находиться в каталоге конфигурации, например:

```powershell
.\build\Debug\NBIoT_CPP_Model.exe
```

Основное приложение создаёт конфигурацию для двух кадров, вызывает только
`DownlinkManager::buildTopology()` и печатает тип каждого сабфрейма:

```text
Топология NB-IoT успешно построена
Кадр 0: [0: NPBCH] [1: NPDCCH] [2: NPDSCH] [3: Empty] [4: Empty] [5: NPSS] [6: Empty] [7: Empty] [8: Empty] [9: NSSS]
Кадр 1: [0: NPBCH] [1: NPDCCH] [2: NPDSCH] [3: Empty] [4: Empty] [5: NPSS] [6: Empty] [7: Empty] [8: Empty] [9: NPDSCH]
Ресурсная сетка пока пуста: алгоритмы не реализованы.
```

Нулевые индексы используются намеренно: в одном кадре номера сабфреймов идут
от 0 до 9. В первом кадре гибкое значение позиции 9 заменено обязательным
NSSS, потому что абсолютный номер кадра равен нулю и является чётным.

### Запуск тестов

По умолчанию `ENABLE_GTEST=ON`. При первой конфигурации CMake загружает
GoogleTest из GitHub, поэтому этот шаг может занять некоторое время и требует
интернета.

```bash
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

### Сборка без GoogleTest

Если нужны только приложения и библиотека, тесты можно отключить:

```bash
cmake -S . -B build-no-tests -DENABLE_GTEST=OFF
cmake --build build-no-tests
./build-no-tests/NBIoT_CPP_Model
```

### Старый демонстрационный пайплайн

Файл `src/pipeline.cpp` сохранён как отдельный пример прежней
алгоритмической работы и больше не является основной точкой входа:

```bash
cmake --build build --target NBIoT_Pipeline_Demo
./build/NBIoT_Pipeline_Demo
```

Это самостоятельный demo-target. Он не проходит через
`nbiot::DownlinkManager` и не является доказательством того, что алгоритмы уже
подключены к новой архитектуре.

    └── subframes/             заглушки будущих алгоритмов

Каталоги `include/code`, `include/sync`, `include/misc` и соответствующие им
части `src/` содержат ранее написанные алгоритмические и вспомогательные
модули. Они сохранены, но пока не связаны с `DownlinkManager`.

## Как читать проект

Новичку удобнее идти в таком порядке:

1. `src/main.cpp` — пример создания конфигурации и менеджера.
2. `include/model/ModelConfig.h` — входные параметры модели.
3. `include/model/DownlinkManager.h` — главный сценарий работы.
4. `include/model/Frame.h` — один кадр и десять принадлежащих ему
   сабфреймов.
5. `include/model/Subframe.h` — общий договор для любого типа сабфрейма.
6. `include/model/SubframeFactory.h` — выбор конкретного класса по enum.
7. `include/model/ResourceGrid.h` — контейнер ресурсных элементов.
8. `include/model/subframes/` — конкретные классы-заготовки.
9. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — подробные диаграммы и
   объяснения.

Новые типы находятся в `namespace nbiot`. Поэтому в коде явно видно, что
`nbiot::Frame` и `nbiot::Subframe` относятся к модели NB-IoT, а не являются
случайными глобальными именами.

## Коротко о правилах сабфреймов

В каждом кадре всегда десять сабфреймов. Менеджер применяет следующие
правила:

| Номер сабфрейма | Тип |
|---:|---|
| 0 | всегда `Npbch` |
| 5 | всегда `Npss` |
| 9 в кадре с чётным абсолютным номером | всегда `Nsss` |
| остальные позиции | значение из `ModelConfig::flexibleSubframes` |
| 9 в нечётном кадре | значение из `ModelConfig::flexibleSubframes[9]` |

Фиксированные правила важнее пользовательской настройки. Например, попытка
поставить `Npdsch` в позицию 0 не заменит NPBCH.

Чётность позиции 9 определяется по **абсолютному** номеру кадра:

```cpp
absoluteFrameNumber = startFrameNumber + frameIndex;
```

Поэтому при `startFrameNumber == 7` первый создаваемый кадр нечётный, даже
если его внутренний индекс в контейнере равен нулю.

## Ресурсная сетка

Для каждого сабфрейма отводится:

- 12 поднесущих;
- 14 OFDM-символов: два слота по семь символов;
- типизированный `ResourceElement` с комплексным значением и меткой
  размещённого канала/сигнала.

После `buildTopology()` вся сетка остаётся пустой: значения равны нулю, а
метки имеют тип `Empty`. Метод `ResourceGrid::at(...)` даёт проверяемый доступ
к элементу и сообщает об ошибке, если индекс выходит за границы.

## Главная граница текущей версии

Вызов:

```cpp
manager.buildTopology();
```

должен успешно построить объекты и пустую сетку.

Вызов:

```cpp
manager.generateResourceGrid();
```

уже относится к будущей алгоритмической стадии. Пока он доходит до первой
заглушки `Subframe::mapTo(...)` и завершает работу исключением с понятным
сообщением. Это защита от опасной ситуации, когда программа молча выдаёт
нули и называет их рассчитанным NB-IoT-сигналом.
